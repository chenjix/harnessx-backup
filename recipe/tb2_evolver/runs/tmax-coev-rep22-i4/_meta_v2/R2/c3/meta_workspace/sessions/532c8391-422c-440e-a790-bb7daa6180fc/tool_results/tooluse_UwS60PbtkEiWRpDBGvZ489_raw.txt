3	"""Stronger self-verification checklist for computation-heavy TB2 tasks.
4	
5	Motivation (evolve-set evidence, no task-specific constants baked in)
6	---------------------------------------------------------------------
7	The stock ``CustomSelfVerifyProcessor`` injects a one-shot checklist when the
8	agent tries to exit with no tool call.  Its step 3 ("inspect the actual file
9	contents ... confirm the values are semantically correct") is passive: it asks
10	the agent to *look* at the output but does not force it to *re-derive* anything
11	or to reconcile its own reasoning with the values it produced.
12	
13	On the evolve set this is the dominant unrecovered failure shape for
14	computation tasks: the agent writes a program that runs cleanly, produces a
15	numerically WRONG answer, and exits via ``no_tool_calls`` fully convinced it is
16	done — even when its own narration contradicts the output.  A representative
17	example in the trajectories: an agent stated in prose that a data window was
18	entirely zero while the value it actually emitted for that window was clearly
19	nonzero, an internal contradiction it never reconciled because the checklist
20	only asked it to "inspect" the file.  The same confident-exit-on-wrong-numbers
21	shape recurs across several data_science / scientific_computing / security tasks
22	(all ``no_tool_calls`` with low step counts).
23	
24	This processor keeps every mechanical property of the stock verifier (fires at
25	most once, on the exit turn, via the same keepalive tool-call trick, +1 user
26	message) but swaps the injected checklist for one that adds two general
27	debugging disciplines:
28	
29	  * **Independent re-derivation** — recompute at least one output value by a
30	    *different* method (e.g. a quick shell/awk/python one-liner over the raw
31	    input) and confirm it matches the value your program wrote.
32	  * **Contradiction sweep** — compare intermediate diagnostics / your own
33	    stated expectations against the final output; if any value looks
34	    surprising or contradicts something you concluded earlier, treat that as a
35	    bug in your program, not a curiosity to rationalise.
36	
37	None of this carries task-specific knowledge: it is a verification *strategy*
38	that applies to any task that produces computed outputs, seen or unseen.
39	"""
40	
41	from __future__ import annotations
42	
43	from benchmarks.terminal_bench_2.harness import CustomSelfVerifyProcessor
44	
45	
46	_CROSSCHECK_MSG = """\
47	Before finishing, run through this verification checklist — do not skip any \
48	step even if you already verified. A program that ran without errors does NOT \
49	mean the answer is correct.
50	
51	1. **Re-read the task description now.** List every requirement, including \
52	edge cases, accuracy thresholds, exact output paths, and exact output format. \
53	Check your solution against each one explicitly.
54	
55	2. **Confirm every required output file exists at its exact path:**
56	```bash
57	ls -lh /path/to/each/required/output/file
58	```
59	Run `ls` explicitly for each required file — do not assume.
60	
61	3. **Inspect the actual contents** of each output file (`cat`/`head`) and read \
62	the values, not just the file size.
63	
64	4. **Independently re-derive at least one output value by a DIFFERENT method** \
65	than the program you wrote — for example a quick shell / awk / python one-liner \
66	that computes the same quantity straight from the raw input — and confirm it \
67	matches what your program emitted. If they disagree, your program has a bug: \
68	fix it before exiting. Silent parsing/offset/type-conversion errors routinely \
69	produce plausible-looking but wrong numbers.
70	
71	5. **Contradiction sweep.** Compare your own earlier reasoning and any \
72	intermediate diagnostics against the final output. If a value looks surprising \
73	or contradicts something you concluded while working (e.g. you expected a \
74	window to be all zeros but its mean is nonzero), that is a symptom of a bug in \
75	your program — investigate and fix it rather than rationalising it away.
76	
77	6. **Validate your verification method.** A test that only checks syntax, \
78	importability, or exit-code-0 on a trivial case is NOT valid — it passes even \
79	on a broken implementation. Make sure you exercised the real behaviour on the \
80	real input.
81	
82	7. **For running services:** confirm they are still alive and reachable right \
83	now, not just that they started earlier.
84	
85	Fix anything that looks wrong before exiting. When all checks pass, end your \
86	final message with:
87	**SUCCESS: task complete. Output files confirmed at [list each required path].**\
88	"""
89	
90	
91	class SelfVerifyCrossCheckProcessor(CustomSelfVerifyProcessor):
92	    """``CustomSelfVerifyProcessor`` with a re-derivation + contradiction checklist.
93	
94	    Reuses the parent's hook mechanics verbatim; only the injected checklist
95	    string is overridden, so the fires-once / exit-turn / keepalive contract is
96	    identical.  The override is applied by pointing the module-level constant
97	    the parent reads (``_SELF_VERIFY_MSG``) at the stronger text while this
98	    processor's message is pending, then restoring it — but simplest and safest
99	    is to set the pending message directly in ``on_after_model``.
100	    """
101	
102	    _singleton_group = "tb2_self_verify"
103	
104	    async def on_after_model(self, event):
105	        # Delegate to the parent to preserve the exact exit-intent detection and
106	        # keepalive-tool-call wiring, then upgrade the pending checklist text.
107	        async for out in super().on_after_model(event):
108	            if self._pending_message:
109	                self._pending_message = _CROSSCHECK_MSG
110	            yield out
