20	### Why
21	
22	R0 scored 29/50. Among the 21 failures, a distinct mechanical cluster
23	of 5 tasks share a shape: the agent issues **byte-identical consecutive
24	Bash tool calls** dozens of times in a row. On task_001321 the same call
25	repeated 55 consecutive times (65 total); on task_000958 the same SQL
26	query repeated 62 times until max_steps; task_000578 repeated a Go-file
27	heredoc 37 times until the context overflowed into an HTTP 400 crash.
28	The agent even emits self-aware text ("Let me try a different approach")
29	yet keeps issuing the identical call — a mechanical repeat the model
30	cannot self-interrupt. No repetition-loop detector exists in the current
31	pipeline; `CustomEditToolProcessor` only counts file-write commands, so
32	non-write loops (query/run) slip through.
33	
34	### Changes
35	
36	- `config.yaml` — insert built-in
37	  `harnessx.processors.control.loop_detection.LoopDetectionProcessor`
38	  after `CompactionProcessor`, before `ParseRetryProcessor`.
39	  Params: window_size=12, warn_threshold=3, threshold=5,
40	  name_warn_threshold=9999 (name-only strategy disabled for single-tool
41	  TB2), compaction_drop_threshold=5. No new code authored — reuse of a
42	  built-in processor.

60	### Uncertainty
61	
62	The warn-at-3 nudge may not break the model out of a loop it is
63	mechanically committed to; in that case raise-at-5 still converts the
64	crash/step-burn into a clean `loop_detected` exit (protects the replay
65	gate and reclaims steps) but does not flip the task to pass. If the 5
66	predicted tasks still fail with the same loop shape next round, the
67	control lever alone is insufficient and we should escalate (e.g. inject
68	a divergence hint on the warn, or a different tool affordance).

100	### Why
101	
102	**Key structural discovery:** the tmax eval path (`recipe/tmax_eval/run_eval.py`
103	→ `agent_loop.run_agent`) is a self-contained loop that does **not** run the
104	harnessx processor pipeline. The only part of `config.yaml` it consumes is the
105	system prompt, resolved by `_resolve_system_prompt`, which reads a
106	`templates/*.j2` (or `system_prompt.txt`) sitting next to the config, else falls
107	back to the bare 5-line `agent_loop.SYSTEM_PROMPT`. Consequently R1's
108	`LoopDetectionProcessor` insertion was inert here (29→30 is within repeat-spread
109	noise per `history/OVERVIEW.md`), and the R0/R1 agents ran with the bare default
110	prompt that has zero guidance on environment survey, planning, exact output
111	paths, or pre-exit verification. The dominant harness-addressable failure cluster
112	in R1 is `finished=no_tool_calls` with a deliverable that is missing, truncated,
113	or off-spec — the agent declared done without verifying its own output against the
114	task's stated requirements. The only behavioral lever exposed on this benchmark is
115	the system prompt.
116	
117	### Changes
118	
119	- `templates/tb2_agent.j2` — new structured system-prompt template (general
120	  strategy: read task + note exact output paths; survey env first; decompose/plan;
121	  write to exact paths; mandatory Definition-of-Done verification of every
122	  deliverable's existence + content + constraints before stopping; background-service
123	  discipline; no `apt-get update`). No task-specific literals.
124	- `config.yaml` — swap `SystemPromptProcessor.system_builder` from
125	  `_StaticSystemPromptBuilder` to `TemplateSystemPromptBuilder` pointing at the
126	  new template via absolute `file://` path (keeps config coherent; the eval loop
127	  picks the template up via `_resolve_system_prompt`). Rest of pipeline unchanged.

144	### Uncertainty
145	
146	The prompt won't fix pure single-chat transport timeouts (010/015/028/264 etc. die
147	on `chat failed: timed out`) or genuine capability/algorithm gaps (396 deviation,
148	1937 grid value, 1781 deadlock logic, security classifier 505/1701) — those are not
149	Instruction-addressable. If the survey/verify discipline adds enough steps that a
150	short passing task now runs long or a mid-work timeout gets triggered more often,
151	pass_rate could dip; the rollback trigger covers that. If R3 shows the verify
152	discipline flips several of the predicted tasks, consider tightening the prompt's
153	step-efficiency guidance.
