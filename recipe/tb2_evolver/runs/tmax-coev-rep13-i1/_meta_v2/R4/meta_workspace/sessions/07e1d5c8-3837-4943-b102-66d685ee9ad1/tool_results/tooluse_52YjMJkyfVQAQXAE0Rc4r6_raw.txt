20	### Why
21	
22	Baseline R0 scored 30/50 (60%). The single clearest cross-cutting failure
23	shape: 5 tasks hit `exit_reason=budget_exceeded` at the 80-step cap
24	(task_000010, task_000118, task_000264, task_001031, task_001321), spanning
25	system_administration, data_querying, data_processing and scientific_computing.
26	Reading their message tails shows the same mechanism every time — the agent
27	stalls and re-issues the *exact same* Bash command verbatim, gets the identical
28	result, narrates "I've been stuck in a loop," and then repeats the command
29	again until it burns all 80 steps. Command histograms confirm it: task_000118
30	ran one command 14×, task_001031 9×, task_001321 7×. The existing recovery
31	processors miss this: `LengthTruncationRecoveryProcessor` only fires on
32	`finish_reason=length` runaways, and `CustomEditToolProcessor` only counts
33	file-writes to the same path, so a repeated query/build/read slides past both.
34	
35	### Changes
36	
37	- `processors/repeat_command_guard.py` — new `RepeatCommandGuard`
38	  (`MultiHookProcessor`). Keys on the exact whitespace-normalised Bash command;
39	  when the same command has run >= `threshold` (3) times it appends an escalating
40	  break-out advisory to that tool's result (redirect first, hard-stop after
41	  `hard_stop_extra` more repeats). Purely additive to the tool result — never
42	  blocks execution, never mutates message history.
43	- `config.yaml` — register the guard at `_order=31` (right after
44	  `CustomEditToolProcessor`) via absolute `file://` path, `threshold: 3`,
45	  `hard_stop_extra: 2`.
46	- `system_prompt.txt` — copied byte-for-byte from R0 (SiblingSystemPromptBuilder
47	  reads it beside the YAML). Unchanged.
48	
49	### Evidence
50	
51	- `task_000264_ab8c7253`: exit_reason=budget_exceeded, 80 steps; body tail —
52	  re-issues identical `sqlite3 company.db "WITH RECURSIVE subordinates ..."`;
53	  tool returns "(exit 0, no output captured)" each time; agent narrates
54	  "I'm still getting no output captured... very strange" then repeats it.
55	- `task_001321_658ce4a8`: exit_reason=budget_exceeded, 80 steps; body tail —
56	  repeats verbatim "I've been stuck in a loop. Let me just run the pipeline..."
57	  and re-issues the same command; tool returns identical
58	  `15 /home/user/clean_codes.txt` each time (maxrepeat=7).
59	- `task_001031_a8f0eb37`: exit_reason=budget_exceeded, 80 steps; loops on the
60	  same mpi4py edit (maxrepeat=9), unchanged tool result, ignores the existing
61	  edit-limit warning.
62	- Contrast (regression guard): passing high-step tasks iterate DIVERSE commands
63	  — task_001818 (passed, 69 steps) 31 distinct commands, task_001089 (passed,
64	  80 steps) 23 distinct — so the exact-match count>=3 gate should not fire on
65	  them meaningfully.
66	
67	### Uncertainty
68	
69	The guard converts "burn 80 steps on one dead command" into "get redirected
70	with steps left"; it does not guarantee the model then solves the underlying
71	task, so flips are probabilistic, not certain. Main risk is a benign identical
72	command (service poll, watch loop) drawing an advisory — but since the message
73	is purely appended to the result and never blocks, worst case is a slightly
74	noisier tool result. Watch R2: if pass_rate doesn't improve and no predicted
75	task flips, and especially if any diverse-command passer regresses, revert.

94	
95	R1 (the incumbent) scored 29/50; the R1 repeat-command guard was accepted
96	but flipped 0/5 of its predicted tasks (task_000010, 000118, 000264,
97	001031, 001321 all still F). Per the scoreboard guidance, a loop lever

101	I swept all 21 R1 failures (frontmatter + message tails + oh_runs traces).
102	The dominant failure shape (≈14 of 21) is **false-confident completion**:
103	the agent ends with "All requirements are met / ✅✅✅ / The task is complete"
104	while reward=0. Passing and failing tasks are behaviourally identical at the
105	tail — both write confident checkbox summaries. The only difference is

107	
108	The one-shot CustomSelfVerifyProcessor already fires on these tasks

113	signal to distinguish a correct "✅ done" from a wrong "✅ done". A stronger
114	self-verify would inflate tokens on all 50 tasks and risk regressing the 29
115	passers for no reliable gain — a net-negative Pareto move.
116	
117	Subtypes of the failing cluster, all model-capability gaps (no harness fix):

122	  the harness cannot inject.

125	- Complex multi-service debugging (task_000028, 000958, 001090, 001937):

191	
192	### Why
193	
194	R2 scored 31/50 (62%). Re-sweeping the failures with a (command, output)
195	fingerprint (not command-string alone, as R1 used) surfaced a clean
196	mechanical cluster the R1 guard could not close: the agent re-issues the
197	EXACT same Bash command and gets BYTE-IDENTICAL output over and over, while
198	narrating "I've been stuck in a loop," until it burns the step budget or
199	hits agent_error. The R1 RepeatCommandGuard fired on these (its advisory
200	text appeared ~10x on task_001652) but was advisory-only — the model ignored
201	it and kept looping. Keying on (command, output) instead of the command
202	string alone separates these dead loops from healthy iterate-and-test loops:
203	passing tasks that re-run a file write many times interleave DIFFERENT
204	build/run output, so their consecutive-identical (cmd,output) count stays at
205	2, far below the block threshold.
206	
207	### Changes
208	
209	- `processors/dead_loop_breaker.py` — new `DeadLoopBreaker` (MultiHookProcessor).
210	  Keys on (normalised_command, sha1(output)). Below block_threshold it appends
211	  an escalating advisory (like R1). At block_threshold (5) identical
212	  (command,output) repeats it intercepts the next identical Bash call in
213	  on_before_tool via approved=False + synthetic_result, so the dead command
214	  does NOT execute — forcing the agent to change command or approach. Counter
215	  resets the instant output changes. Empty-argument calls (no command) ignored.
216	- `config.yaml` — replace the R1 RepeatCommandGuard block with DeadLoopBreaker
217	  at the same _order=31 slot, advisory_threshold 3, block_threshold 5, absolute
218	  file:// path.
219	- `system_prompt.txt` — copied byte-for-byte from R2 (unchanged).
220	
221	### Evidence
222	
223	- task_001652_86e1d185 (FAIL, agent_error): last messages repeat verbatim "I've
224	  been stuck in a loop trying to extract text from the image. Let me take a
225	  fundamentally different approach..." then re-issue the SAME python3 heredoc
226	  pixel-scan command; tool returns identical "White pixels in row 32: 54 ..."
227	  each time. Measured 12 identical (command,output) pairs; R1 advisory appeared
228	  ~10x and was ignored.
229	- task_001536_acfe6c35 (FAIL): measured 8x identical sanitize-script write plus
230	  a rm-and-ls diagnostic returning identical "Exit code: 0 ... output directory
231	  contents"; 7x command-repeat run to the cap.
232	- task_001032_1adaccb9 (FAIL): measured 4x identical od-hexdump-grep diagnostic
233	  with identical hexdump output each time.
234	- Regression guard (PASSING tasks, measured consecutive-identical (cmd,output)):

236	  differs); task_001089 24x is the empty-argument call (excluded, no command);
237	  task_001818 / task_000578 max 2. block_threshold 5 clears all.
238	
239	### Uncertainty
240	
241	The block converts "0 steps left in a dead loop" into "steps left, forced off
242	the dead command" — strictly better on budget, but it does not guarantee the
243	model then solves the underlying (often hard) task, so flips are probabilistic.
244	Main regression risk is a benign identical-output re-run reaching the threshold;
245	no observed passer does (max 2). Watch R4: if pass_rate doesn't improve and none
246	of the three predicted tasks flip, or any high-repeat passer regresses, revert.
