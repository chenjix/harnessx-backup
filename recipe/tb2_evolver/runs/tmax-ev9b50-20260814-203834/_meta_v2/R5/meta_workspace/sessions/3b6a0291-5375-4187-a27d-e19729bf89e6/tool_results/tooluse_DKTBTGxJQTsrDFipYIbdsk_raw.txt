20	### Why
21	
22	R0 scored 30/50 (60%). Of the 20 failures, 7 share one exact mechanism:
23	`status=agent_error`, `agent.exit_reason=error`, and very high `elapsed_s`
24	(352–1160s). Every one of these 7 tasks — and no others — contains the run
25	loop's user nudge "Your previous response was cut off by the token limit.
26	Please continue from where you left off." The mechanism: the small model
27	(Qwen3.5-9B) enters a degenerate repetition loop, emitting the same narration
28	paragraph hundreds of times in the assistant `content` field with no tool
29	call until it hits `max_tokens` (`finish_reason=length`). The run loop's
30	`runloop.py` then appends a *passive* "please continue" nudge, which merely
31	re-primes the same runaway generation. The cycle repeats until the container
32	errors out. This cuts across system_administration, data_querying,
33	software_engineering, security, and data_processing domains — a harness
34	deficiency, not a domain-knowledge gap.
35	
36	The remaining 13 failures are heterogeneous capability gaps (wrong recursive
37	SQL / index creation in task_000264, wrong output paths, domain logic errors)
38	with no shared harness lever — no harness fix; skip.
39	
40	### Changes
41	
42	- `processors/length_recovery.py` — new `LengthTruncationRecoveryProcessor`
43	  (Control). `on_after_model`: on `finish_reason=length` with no tool call,
44	  collapse runaway `content` to a head+tail excerpt and arm a corrective
45	  nudge; reset streak on any normal/tool-calling turn. `on_before_model`:
46	  append exactly one `user` message redirecting the model to stop narrating
47	  and issue a single concrete Bash command, escalating on consecutive
48	  truncations.
49	- `config.yaml` — register the processor (`_order=5`, early in the
50	  after-model chain) via absolute `file://` path, between
51	  `TaskTimeReminderProcessor` and `CompactionProcessor`.

94	### Why
95	
96	R1's LengthTruncationRecoveryProcessor worked as intended: the
97	status=agent_error (finish_reason=length crash) cluster dropped from 7 to 2,
98	and R1 scored 31/50. But a distinct failure shape now dominates the slow
99	failures: several tasks end each turn normally (a well-formed Bash tool call,

101	reacting to the result. They grind to the ~33-step cap and time out with reward
102	0 (task_000264 4307s, task_001818 3144s, task_000118 1931s, task_001031 1433s,
103	task_000010 964s). The existing CustomEditToolProcessor emits a passive
104	EditDetection text warning on over-writes, but the model ignores it and keeps
105	looping. This is a cross-domain harness deficiency, not a domain-knowledge gap.
106	
107	### Changes
108	
109	- processors/repeat_command_breaker.py — new RepeatedCommandBreakerProcessor
110	  (Control, order=40, after EditDetection, before self-verify). on_before_tool:
111	  normalize each Bash command (whitespace-collapse) and count consecutive
112	  identical repeats; at streak 3+ arm a soft redirect nudge, at 4+ a hard one,

114	  loop physically cannot continue. on_before_model: append exactly one user
115	  redirect (contract-safe +1). Streak resets on any different command / task
116	  boundary.
