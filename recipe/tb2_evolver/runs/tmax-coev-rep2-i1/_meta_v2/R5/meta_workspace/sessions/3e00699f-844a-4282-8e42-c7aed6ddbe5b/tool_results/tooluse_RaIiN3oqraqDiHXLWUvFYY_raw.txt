20	### Why
21	
22	R0 = 29/50. A distinct `budget_exceeded`-at-80-steps cluster (010,
23	118, 264, 958, 1321, 1701, 1818) shares one shape: the model emits a
24	paragraph of narration with no tool call, hits `max_tokens`
25	(`finish_reason=length`), the run loop appends a passive "continue"
26	nudge, and the model re-emits the SAME narration. The stock
27	`LengthTruncationRecoveryProcessor` fires correctly (corrective nudge +
28	truncation marker seen 33-39x per looping task in JSONL) but does not
29	break the loop: each truncated turn's full narration is persisted, so
30	by step 50 the model sees its own repeated prose ~6x in context (verified
31	in task 264) and re-primes the identical runaway generation. The nudge
32	is not the missing piece — the persisted repeated narration is.
33	
34	### Changes
35	
36	- `processors/length_loop_deprime.py` — new `LengthLoopDeprimeProcessor`
37	  (same singleton group `tmax_length_recovery`, same `_order=5`) that
38	  replaces the stock recovery processor. On repeated consecutive
39	  length-truncations (`>= deprime_after=2`) it drops the runaway
40	  narration to a compact stub (history stops re-showing the loop text)
41	  and escalates the user nudge to a hard "single Bash command, no prose"
42	  directive. First truncation retains the stock head+tail collapse.
43	- `config.yaml` — swap `recipe.tmax_eval.processors.length_recovery.
44	  LengthTruncationRecoveryProcessor` for the `file://` authored
45	  processor; add `deprime_after: 2`.

47	### Evidence
48

50	  ~70 messages, JSONL shows 33-39 length-truncation recovery firings — the

53	  re-priming identical output. In 958 the narration already NAMED the real
54	  bug ("near backups: syntax error") but never issued the fix command.
55	- Pareto guard: passing tasks reach 40-98 messages (001536=98, 001652=88,
56	  001498=76) — proving message-count threshold tuning would regress them.
57	  The distinguishing signal is truncation-recurrence, not length, which is
58	  exactly what this processor gates on. Threshold tuning explicitly rejected.
59

87	### Why
88	
89	R1 (accepted, 29->32/50, +3/-0) de-primed the pure-narration finish_reason=length
90	loop. But the residual budget_exceeded-at-80-steps cluster re-manifested with a
91	different shape: the model now issues a tool call every turn but re-issues the

93	produces the task required output artifacts. Fingerprinting the R1 messages logs:
94	958 = 33/33 identical, 1818 = 27/29, 1032 = 25/29, 264 = 21 consecutive identical

96	(identical-command repetition, not length truncation) and no existing guard closes it.

98	### Changes

104	  artifacts; stop re-running the same command) and a hardened one at escalate_at=5.
105	  Warn-only - never raises. Contract-safe (mutates only ToolResultEvent.result).
106	- config.yaml - insert the processor after LengthLoopDeprimeProcessor, before
107	  CompactionProcessor.

242	### Changes
243	
244	- `templates/tmax_system_prompt.j2` — new system-prompt template. Keeps the
245	  original 5 stub lines verbatim, then appends GENERAL execution discipline:
246	  (1) survey the environment/toolchain before building; (2) enumerate EVERY
247	  success criterion up front, explicitly including non-file / process-state /
248	  absence / numeric-threshold conditions; (3) before declaring done, run a
249	  concrete command that exercises EACH criterion (not just file existence) and

251	  problems.

253	  `SiblingSystemPromptBuilder` (5-line stub) to `TemplateSystemPromptBuilder`
