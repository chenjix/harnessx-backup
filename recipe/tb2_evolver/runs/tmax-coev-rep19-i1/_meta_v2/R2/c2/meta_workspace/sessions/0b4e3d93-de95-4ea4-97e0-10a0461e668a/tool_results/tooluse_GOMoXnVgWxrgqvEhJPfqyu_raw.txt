20	### Why
21	
22	Assigned focus `task_000010_644ab1c2` (system_administration) fails with
23	`exit_reason=budget_exceeded` at the 80-step cap after 889s. The task requires
24	writing `/home/user/operator.py`; running Python with cwd=`/home/user` makes the
25	file shadow the stdlib `operator` module and breaks the interpreter. The model
26	correctly diagnosed this but then entered a degenerate loop: ~15 near-verbatim
27	"I've been stuck ... circular import ... only real solution is to rename the
28	file, but the user asked for /home/user/operator.py" turns, interleaved with 16
29	passive "cut off by the token limit" continue nudges. It never tried the actual
30	fix (run Python from another cwd / set PYTHONPATH) because its own runaway prose
31	kept re-priming the identical completion. Six tasks total die this way at
32	exactly steps=80. The existing `LengthTruncationRecoveryProcessor` only fires on
33	`finish_reason=length AND no tool_calls` and its nudge text never appears in any
34	trajectory (`proc_nudge=0`); a soft one-line nudge cannot outweigh the wall of
35	repeated prior turns. Critically, `task_001321_658ce4a8` re-issues a
36	**byte-identical Bash command 33 times** — a prior-rep loop breaker that resets
37	on any tool call would never catch it.
38	
39	### Changes
40	
41	- `processors/repetition_loop_breaker.py` — new `RepetitionLoopBreaker`
42	  `MultiHookProcessor`. Fingerprints each assistant turn as
43	  (normalised content prefix + tool-call name/input signature); on 3 consecutive
44	  matching turns it prunes the duplicate looping turns (plus their paired tool
45	  results and passive nudges) from the assembled context in `on_before_model`
46	  and appends ONE decisive "abandon this line, take a different concrete step"
47	  redirect. Content-agnostic — names no task, path, command, or constant.
48	- `config.yaml` — register the processor after `LengthTruncationRecoveryProcessor`
49	  (order 6) and before compaction.

64	### Uncertainty
65	
66	The breaker guarantees the loop stops and the budget is reclaimed for fresh
67	attempts, but it does not inject the missing solution knowledge (e.g. the cwd /
68	PYTHONPATH trick for task_000010) — that is a model capability. So a flip is
69	plausible but not certain; the sure win is eliminating the 0-progress budget
70	burn. If the redirect proves too aggressive and prunes a legitimate retry chain,
71	a previously-passing task would truncate — watch for T→F regressions with
72	truncated exits and revert if seen alongside a flat/down pass_rate.
