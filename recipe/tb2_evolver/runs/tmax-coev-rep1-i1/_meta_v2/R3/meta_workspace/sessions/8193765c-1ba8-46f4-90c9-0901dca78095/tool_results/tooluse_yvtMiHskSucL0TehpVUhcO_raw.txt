18	### Why
19	
20	R0 = 29/50 (0.58). The dominant failure mode is a max_tokens runaway
21	loop: the small model (Qwen3.5-9B) emits an enormous no-tool-call
22	narration turn (104K-329K chars) that hits the provider output cap.
23	The runloop (harnessx/core/runloop.py:734) then appends a passive
24	"Your previous response was cut off by the token limit. Please
25	continue from where you left off." nudge, which re-primes the exact
26	runaway generation while the 300KB blob pollutes the next context
27	window. The cycle burns steps/wall-clock (up to 74 steps, 964s) and
28	terminates in `exit_reason=error` with the required output file never
29	written. All 11 `exit_reason=error` tasks in R0 exhibit >=1 cut-off
30	nudge; 8 of them failed. Max assistant-turn size is cleanly bimodal:
31	passing cluster tops out at ~14.8K chars, runaway cluster starts at
32	104K — a 40K threshold sits in the empty band and cannot misfire.
33	
34	### Changes
35	
36	- `processors/length_recovery.py` — new `LengthTruncationRecoveryProcessor`
37	  (`MultiHookProcessor`). `on_after_model`: detect a no-tool-call turn
38	  with `finish_reason=="length"` OR `content>=40000` chars, collapse
39	  the blob to head+tail excerpt, arm an escalating nudge, count
40	  consecutive occurrences. `on_before_model`: inject exactly one user
41	  message redirecting the model to a single concrete Bash command
42	  (gentle first, forceful on repeat). Trigger keys only on structural
43	  signals — benchmark-agnostic.
44	- `config.yaml` — register the processor via absolute `file://` path,
45	  inserted after `TaskTimeReminderProcessor` and before
46	  `CompactionProcessor` (so the collapsed content reaches compaction).
47

53	- `task_000264_ab8c7253`: 328.9K-char turn re-deriving subordinate

55	- `task_000015_89886d8d`: 286.6K-char OCR-schema narration, cut-off

57	- `task_001032_1adaccb9`: 128.4K-char tar-header hex-dump narration

59	- Bimodal check: passing max assistant turn = 14.8K chars

61	  (task_000818_315382d9, which passed but wasted 437s). No passing
62	  task lands between 14.8K and 104K.
63	
64	### Uncertainty
65	
66	The nudge redirects the model to "one concrete Bash command"; if the
67	underlying task genuinely needs the model to reason more before
68	acting, the redirect could push a premature command. Mitigated
69	because the streak resets on any normal turn, so the model regains
70	freedom immediately after acting. Signal to watch: if the 2
71	loop-survivor passes regress or overall pass_rate drops, revert.
72	This exact processor lineage (tmax-ev9b50 R6) was built against the
73	identical bimodal signature, giving prior evidence it lands.

92	### Why
93	
94	R1 (accepted) eliminated every R0 exit_reason=error by collapsing the
95	max_tokens narration blobs, but pass_rate stayed at 29/50 — the runaway
96	loops merely re-manifested as budget_exceeded (80 steps) or slow done
97	finishes. The dominant remaining failure shape is a degenerate loop of
98	identical consecutive Bash tool calls. maxrun (longest run of identical
99	consecutive tool-call argument strings) cleanly separates the failing loop
100	cluster (16-26 repeats) from the entire passing cluster (all <=7). The
101	pipeline had NO loop-detection processor wired in, so exit_reason=loop_detected
102	never fired and these tasks consumed the full step/wall budget. Fix: wire the
103	in-tree, benchmark-agnostic LoopDetectionProcessor with warn-at-3 (recovery
104	nudge injected into the tool result before the budget is spent) and a
105	raise-at-10 hard stop (safely above the one passing task's run of 7).
106	
107	### Changes
108	
109	- config.yaml — insert harnessx.processors.control.LoopDetectionProcessor
110	  after CompactionProcessor (its _order=20 runs after compaction's _order=8 so
111	  its compaction-drop reset sees the evicted window). Params: window_size=12,
112	  warn_threshold=3, threshold=10, name_warn_threshold=8,
113	  compaction_drop_threshold=5. No new files authored — reuse tested in-tree code.
114

131	### Uncertainty
132	
133	Hard termination alone does not hand a looping task a correct answer — the
134	net-positive claim rests on the warn-at-3 recovery nudge giving the agent
135	~60 recovered steps (loops start early: step ~2-4) plus best-output recovery on
136	budget-exhausted tasks. If pass_rate is flat and only cost drops, the warn nudge
137	failed to flip and the change is a pure cost win (still Pareto-positive). Signal
138	to watch: task_001701 regression or any new loop_detected on a previously-passing
139	task -> revert or raise the threshold.
