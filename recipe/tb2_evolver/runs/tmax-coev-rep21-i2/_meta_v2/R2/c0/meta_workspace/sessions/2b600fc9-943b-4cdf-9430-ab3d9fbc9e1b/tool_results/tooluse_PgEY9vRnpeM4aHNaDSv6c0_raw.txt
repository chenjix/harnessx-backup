20	### Why
21	
22	Assigned focus `task_000010_644ab1c2` fails at `budget_exceeded`/80
23	steps. Root cause: the task mandates writing `/home/user/operator.py`,
24	which shadows stdlib `operator`; since CWD is `sys.path[0]`, every
25	`python3` run circular-imports and crashes the interpreter (and the
26	pytest verifier). The model *identified* the cause but never applied
27	the fix (`python3 -P` / `PYTHONSAFEPATH` / different CWD) — a model
28	capability gap. The harness deficiency it exposes is systemic: the
29	model got trapped issuing the exact same failing command cycle ~10
30	times with zero corrective feedback. Sweeping the round, 12 of 50
31	tasks hit `budget_exceeded` at exactly 80 steps, and their command
32	histograms are dominated by a single Bash command repeated 13-29x
33	verbatim and consecutively (task_001031: 29x, task_000011: 27x,
34	task_001382/000477: 26x, task_000313: 18x, task_001207: 13x). No R0
35	processor detects action-level loops — the installed
36	`LengthTruncationRecoveryProcessor` only handles the distinct
37	`finish_reason=length`-with-no-tool-call shape.
38	
39	### Changes
40	
41	- `config.yaml` — add
42	  `harnessx.processors.control.loop_detection.LoopDetectionProcessor`
43	  (previously absent) with `warn_threshold=3`, `threshold=8`,
44	  `name_warn_threshold=999`, `window_size=12`. Warns (redirects) on
45	  each repeated-identical Bash call from repeat 3, raises
46	  `LoopDetectedError` at repeat 8. No new code authored — reuses the
47	  vetted in-tree processor. `LoopDetectedError` maps to
48	  `exit_reason=loop_detected` (runloop.py:781), not `error`, so it
49	  does not trip the replay crash gate.
50	- `system_prompt.txt` — copied byte-for-byte from R0 (sidecar for
51	  `SiblingSystemPromptBuilder`; unchanged).

98	### Why
99	
100	Assigned focus was `task_000028_7fe033ac`. The agent actually SOLVED it — it
101	fixed the nginx socket path, fixed/compiled/ran the C++ server, wrote the
102	logrotate config, and verified `http://127.0.0.1:8080/` returns `150` through
103	nginx ("Integration test PASSED!"). Reward is still 0 because the *verifier*
104	phase crashes at collection: `/tmp/test_final_state.py:6: import requests` →
105	`ModuleNotFoundError: No module named 'requests'`. The verifier's pytest module
106	uses `requests` to probe the HTTP service, but the eval container's system
107	Python does not ship it. Per the tb2-playbook, verifier test files are injected
108	after the agent session ends, so the agent cannot see or infer this dependency
109	— an environment deficiency, not a capability gap. This is systemic: 5 of 41
110	failing tasks fail with the identical `requests` ImportError at verifier
111	collection, and all 5 are HTTP/socket service tasks.
112	
113	### Changes
114	
115	- `processors/verifier_dep_ensure.py` — new `VerifierDepEnsureProcessor`
116	  (Control). On `on_task_start`, for service-shaped tasks (regex over the task
117	  description), best-effort ensures `requests` imports in the system Python
118	  (`python3 -c 'import requests' || pip install requests || true`). Idempotent,
119	  contract-neutral (never touches `event.messages`), never raises.
120	- `config.yaml` — registered the processor via absolute `file://` path early in
121	  the pipeline (`_order=5`, before the model ever runs).
122	- `system_prompt.txt` — copied byte-for-byte from R0 (SiblingSystemPromptBuilder
123	  reads it next to the config; unchanged).
