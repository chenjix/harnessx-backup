20	### Why
21	
22	R0 = 29/50. A distinct `budget_exceeded`-at-80-steps cluster (010,
23	118, 264, 958, 1321, 1701, 1818) shares one shape: the model emits a
24	paragraph of narration with no tool call, hits `max_tokens`
25	(`finish_reason=length`), the run loop appends a passive "continue"
26	nudge, and the model re-emits the SAME narration. The stock
27	`LengthTruncationRecoveryProcessor` fires correctly (corrective nudge +
28	truncation marker seen 33-39x per looping task in JSONL) but does not
29	break the loop: each truncated turn's full narration is persisted, so
30	by step 50 the model sees its own repeated prose ~6x in context (verified
31	in task 264) and re-primes the identical runaway generation. The nudge
32	is not the missing piece — the persisted repeated narration is.
33	
34	### Changes
35	
36	- `processors/length_loop_deprime.py` — new `LengthLoopDeprimeProcessor`
37	  (same singleton group `tmax_length_recovery`, same `_order=5`) that
38	  replaces the stock recovery processor. On repeated consecutive
39	  length-truncations (`>= deprime_after=2`) it drops the runaway
40	  narration to a compact stub (history stops re-showing the loop text)
41	  and escalates the user nudge to a hard "single Bash command, no prose"
42	  directive. First truncation retains the stock head+tail collapse.
43	- `config.yaml` — swap `recipe.tmax_eval.processors.length_recovery.
44	  LengthTruncationRecoveryProcessor` for the `file://` authored
45	  processor; add `deprime_after: 2`.
46	
47	### Evidence
48	
49	- `task_000264` / `task_000958` / `task_001818`: `exit_reason=budget_exceeded`,
50	  ~70 messages, JSONL shows 33-39 length-truncation recovery firings — the
51	  loop never converts to a tool call.
52	- `task_000264` step-50 context: the same narration paragraph appears ~6x,
53	  re-priming identical output. In 958 the narration already NAMED the real
54	  bug ("near backups: syntax error") but never issued the fix command.
55	- Pareto guard: passing tasks reach 40-98 messages (001536=98, 001652=88,
56	  001498=76) — proving message-count threshold tuning would regress them.
57	  The distinguishing signal is truncation-recurrence, not length, which is
58	  exactly what this processor gates on. Threshold tuning explicitly rejected.
59	
60	### Uncertainty
61	
62	The de-prime reclaims budget and de-primes context, but whether the weak
63	model then converts its (correct) diagnosis into the right command is a
64	capability question — flips are plausible, not guaranteed. If R2 shows no
65	flips in the cluster AND no regressions, the mechanism is safe but
66	insufficient (consider pairing with a repeated-action breaker next round).
67	If any passing long-horizon task regresses, revert immediately.

87	### Why
88	
89	R1 (accepted, 29->32/50, +3/-0) de-primed the pure-narration finish_reason=length
90	loop. But the residual budget_exceeded-at-80-steps cluster re-manifested with a
91	different shape: the model now issues a tool call every turn but re-issues the
92	EXACT SAME Bash command over and over, each returning the same result, and never
93	produces the task required output artifacts. Fingerprinting the R1 messages logs:
94	958 = 33/33 identical, 1818 = 27/29, 1032 = 25/29, 264 = 21 consecutive identical
95	heredoc writes to an intermediate SQL file. This is a genuinely new signal
96	(identical-command repetition, not length truncation) and no existing guard closes it.
97	
98	### Changes
99	
100	- processors/repeated_command_breaker.py - new RepeatedCommandBreakerProcessor
101	  (singleton group tmax_repeated_command_breaker, _order=21). On consecutive
102	  identical tool-call fingerprints it appends an escalating, deliverable-grounded
103	  directive to the tool result at warn_at=3 (verify/produce the required output
104	  artifacts; stop re-running the same command) and a hardened one at escalate_at=5.
105	  Warn-only - never raises. Contract-safe (mutates only ToolResultEvent.result).
106	- config.yaml - insert the processor after LengthLoopDeprimeProcessor, before
107	  CompactionProcessor.
108	
109	### Evidence
110	
111	- task_000264 last 16 messages: identical heredoc write to an intermediate SQL
112	  file re-issued back-to-back, each returning (exit 0, no output captured); the
113	  [EditDetection] over-editing warning fires 3x and is IGNORED - proving the
114	  generic nudge is too weak for this model. A grep of all 29 tool-call args finds
115	  ZERO references to the required deliverables (the two named output files): the
116	  agent had a correct recursive CTE but never ran it to produce output.
117	- task_000958 repeated command (33x): a broken-server restart loop
118	  (pkill; run server; ps grep), no progress.
119	- Pareto guard (why warn-only, not the stock raise): task_000536 (audit script
120	  re-written 27x) and task_001089 (malformed empty tool call 27x) BOTH PASS despite
121	  27 consecutive identical calls. The identical-command signature does not
122	  discriminate pass from fail, so LoopDetectionProcessor raise-at-5 would be a
123	  2-task regression. Passing long-horizon tasks otherwise have
124	  max_consec_identical < 3 and are untouched.
125	
126	### Uncertainty
127	
128	The directive is advisory; a weak model may ignore it just as it ignored the
129	edit-warning on 264 (the escalation + deliverable-grounding is the bet on why it
130	lands this time). For the C++ HTTP microservice tasks (958, 1701) the block is a
131	capability gap - this reclaims budget/cost but a flip is not expected there. If R3
132	shows no flips AND no regressions, the mechanism is safe but the remaining cluster
133	is capability-bound; if 536/1089 regress, revert immediately.
