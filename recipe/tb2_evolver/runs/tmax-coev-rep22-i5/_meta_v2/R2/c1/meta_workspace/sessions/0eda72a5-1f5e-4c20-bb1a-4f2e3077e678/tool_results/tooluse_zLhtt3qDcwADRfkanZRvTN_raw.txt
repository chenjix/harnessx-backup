20	### Why
21	
22	Assigned focus task_000010_644ab1c2 (create `/home/user/operator.py`) failed
23	`budget_exceeded` at 80 steps with reward=0. The agent correctly diagnosed the
24	real bug — naming the script `operator.py` triggers a Python stdlib circular
25	import (`from operator import eq` in `collections`) — and a working script
26	already existed at `k8s_operator.py`. But it then entered a degenerate loop:
27	16 of 33 assistant turns were content-only, hit `finish_reason=length`, and were
28	followed by the run-loop's passive "Your previous response was cut off by the
29	token limit. Please continue from where you left off." nudge, which re-primed the
30	same runaway narration. A single `mv` would have passed; the loop never let a
31	tool call out. This is systemic: 7 R0 tasks (task_000958, task_001857,
32	task_001116, task_001098, task_001032, task_001837, plus 000010) show the same
33	content-only length-truncation loop, all reward=0. The existing
34	`LengthTruncationRecoveryProcessor` only *nudges* (rewrites the passive message);
35	it never prunes the re-priming narration or hard-stops a non-recovering loop, so
36	the whole budget burns.
37	
38	### Changes
39	
40	- `processors/length_loop_breaker.py` — new `LengthLoopBreaker` MultiHookProcessor.
41	  Counts consecutive content-only `finish_reason=length` turns (`on_after_model`);
42	  any tool call resets. At `prune_after=3` it prunes the accumulated truncation
43	  narration + passive nudges from the context tail (keeps first message and all
44	  tool exchanges) and injects one hard "emit ONE Bash call" directive
45	  (`on_before_model`). At `hard_stop_after=6` it raises `LoopDetectedError` to
46	  reclaim the remaining step budget.
47	- `config.yaml` — register `LengthLoopBreaker` (via absolute `file://`) directly
48	  after `LengthTruncationRecoveryProcessor` (`_order=6`, so it escalates only
49	  after the per-turn nudge layer has run).

67	### Uncertainty
68	
69	The main risk is a false hard-stop on a task that would have self-recovered past
70	6 consecutive length-truncations. Evidence argues against this: the observed R0
71	loops ran 13–16 truncations without ever recovering, so 6 is well past the point
72	nudging has proven futile, and `keep_recent_pairs=1` keeps the model aware it was
73	just told to stop. If a previously-passing task newly fails with
74	`exit_reason=loop_detected` and little real tool activity, raise `hard_stop_after`
75	or revert.
