20	### Why
21	
22	Baseline R0 = 11/50 (22%). Two tasks (task_001044_45c70cf1,
23	task_000444_250abeda) came back with `status=agent_error` /
24	`exit_reason=error`. Their episode traces both end with a hard
25	`BadRequestError: 400 — This model's maximum context length is 65536 tokens.
26	However, you requested 4096 output tokens and your prompt contains at least
27	61441 input tokens`. The eval model (qwen35-9b-tmax-coev-r12) has a real 65536
28	context window; harness_runner reserves max_tokens=4096 for output, leaving a
29	~61440-token input ceiling. The pipeline's `CompactionProcessor.token_threshold`
30	was 140000 — calibrated for a 128k+ model and therefore unreachable here, so
31	compaction never fired and long histories overflowed the window into an
32	API-level 400 that crashes the whole task. This is a pure harness
33	mis-calibration, not a model capability gap.
34	
35	### Changes
36	
37	- `config.yaml` — `CompactionProcessor.token_threshold` 140000 → 40000.
38	  `rough_token_count` (cl100k) under-counts the real request by ~9-10k
39	  (system prompt + Bash tool schema + Qwen/cl100k tokenizer skew), so firing
40	  at 40000 rough tokens (~50k real) keeps every request safely below the
41	  61440 ceiling with margin for the 6-message retention window.
42	- `system_prompt.txt` — copied byte-for-byte from R0 (sibling required by
43	  `SiblingSystemPromptBuilder`; unchanged).
44	
45	### Evidence
46	
47	- `task_001044_45c70cf1` trace `task_end` step 43: `exit_reason=error`,
48	  error = "maximum context length is 65536 tokens ... prompt contains at least
49	  61441 input tokens". step_start rough `token_count` climbed
50	  40435 → 43408 → 46381 → 49354 with the compaction threshold at 140000 never
51	  approached; the next request overflowed.
52	- `task_000444_250abeda` trace `task_end`: identical
53	  "maximum context length is 65536 tokens" 400 error; history bloated by a
54	  degenerate verbatim-repeat loop (assistant repeated the same
55	  "Let me try a different approach…" paragraph across multiple steps).
56	- Passing cluster peaked far below 40000 rough tokens (max ~13k), so the new
57	  threshold leaves them untouched.
58	
59	### Uncertainty
60	
61	Both target tasks are hard reverse-engineering problems (disassembly / oracle
62	smoothing) and may still fail on correctness after the crash is removed — the
63	win here is converting an infrastructure-guaranteed 0 into a fair run, plus
64	protecting the long-context cluster from the same overflow. If pass_rate does
65	not hold or a passing task regresses with a compaction boundary in its trace,
66	revert to 140000.

151	
152	### Why
153	
154	R1 removed context-overflow crashes; R2 broke identical-command loops. No
155	exit_reason=error remain and several R2 loopers now exit done/short. The
156	dominant harness-caused remaining failure is a service-persistence bug on
157	HTTP/socket tasks. HarborSandbox.exec runs every command inside a setsid'd
158	bash process group, and kill_running() sends SIGTERM to that command's process
159	group between calls / on timeout. A server the agent starts as a plain
160	background job inherits the exec'd bash's PGID, so it is SIGTERM'd (exit 143,
161	defunct zombies) and is no longer listening when the external verifier probes
162	it (Connection refused). The agent has the capability to fix this (setsid is
163	in the image) but lacks the knowledge that a service must be detached into its
164	OWN new session to survive — a pure Instruction gap, not a model capability
165	gap.
166	
167	### Changes
168	
169	- system_prompt.txt (R3 sidecar beside config.yaml, read by
170	  SiblingSystemPromptBuilder) — extended the R2 5-line prompt with a general
171	  strategy: keep required long-running services alive by launching them
172	  detached in their own new session (setsid ... < /dev/null &), and re-confirm
173	  the listener is still up before finishing; plus an external-checker-style
174	  verify-before-exit reminder. Strategy-only; no task-specific literals, ports,
175	  paths, or process names.
176	- config.yaml — copied from R2 byte-for-byte except the header comment, updated
177	  to document the R3 sidecar change. Processor pipeline, knobs, and file://
178	  references unchanged.
179

185	  narrates "The server was killed again." Final launch (step 77) also
186	  (exit 143) -> verifier: Connection refused on 127.0.0.1:8443.
187	- task_000097_d9d1d187 verifier output_tail: "Connection refused. Is the
188	  service listening on 127.0.0.1:9090?" — server not alive at verify.

227	
228	### Why
229	
230	The R0 `VerifierDepGuardProcessor` installs verifier test-deps (`requests`,
231	`pyyaml`) only on exit intent - the model ending its turn with no tool call.
232	But a cluster of tasks (task_000796, task_000910, task_002108) exhaust the
233	80-step budget mid-work (`exit_reason=budget_exceeded`) and NEVER reach exit
234	intent, so the guard never fires. Their hidden `test_final_state.py` does
235	`import requests`; the image lacks it, so pytest aborts at COLLECTION time with
236	`ModuleNotFoundError` -> a deterministic structural 0 no matter what the final
237	container state is. R3 logged this as deferred C-004; this round ships the fix
238	as C-005 (distinct hypothesis id, distinct implementation shape - budget-aware
239	trigger - not a re-proposal of a reverted bet).
240	
241	### Changes
242	
243	- `processors/verifier_dep_guard_budget.py` - new
244	  `BudgetAwareVerifierDepGuardProcessor` (order 96, own singleton group). Fires
245	  the same idempotent dep-ensure Bash call on the first no-tool-call turn once
246	  `step_id >= max_steps - budget_margin` (margin 6), OR on exit intent -
247	  whichever first. `max_steps` read from `StepStartEvent.task`; fallback 80.
248	  At-most-once per task; only on turns with no model tool call; guarded per-module
249	  import check -> pure no-op when deps already present.
250	- `config.yaml` - register the new processor immediately after the R0
251	  exit-intent guard; kwargs budget_margin 6, fallback_max_steps 80.
252	
253	### Evidence
254	
255	- task_000796 / task_000910 / task_002108 `result.json`:
256	  `exit_reason=budget_exceeded`, reward 0; all 80 steps consumed.
257	- `messages.json` for all three: no clean exit-intent turn appears (the run
258	  ends on budget), confirming the R0 exit-only guard's trigger is never met;
259	  narration-only no-tool turns recur near the ceiling (task_002108: 12), which
260	  the budget-approach trigger latches onto to fire before step 80.
261	- Verifier `test_final_state.py` opens with `import requests`; container lacks
262	  it -> collection-time `ModuleNotFoundError` is deterministic.
263	
264	### Uncertainty
265	
266	This removes a structural floor; it does not guarantee content-correctness -
267	these tasks may still fail on wrong values / dead services (a capability gap).
268	The guaranteed effect is converting collection-error 0s into fair scored runs.
269	If R5 shows no flips AND no regressions, the change is cost-neutral insurance
270	and can stay; if it causes any T->F regression, revert per the rollback trigger.
