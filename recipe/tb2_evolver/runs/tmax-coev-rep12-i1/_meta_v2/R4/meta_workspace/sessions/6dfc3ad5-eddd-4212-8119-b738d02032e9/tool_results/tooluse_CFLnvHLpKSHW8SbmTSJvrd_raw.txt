20	### Why
21	
22	R0 scored 29/50 (58%). Analysis of the 21 failing trajectories showed a
23	dominant, mechanical failure shape: the agent issues the SAME Bash command
24	repeatedly, receives the SAME output every time, and makes zero progress
25	until it either exhausts the 80-step budget (`exit_reason=budget_exceeded`,
26	5 tasks) or crashes (`exit_reason=error`, task_002108). Counting maximal
27	runs of consecutive identical commands over `.messages.json`: task_002108
28	= 44, task_000470 = 28, task_000840 = 10 (paired cmd+output), task_000908
29	= 8 (paired). The existing `LengthTruncationRecoveryProcessor` only fires on
30	`finish_reason=length`; these loops have a normal finish reason plus a real
31	(repeated) tool call, so nothing in the pipeline intercepted them.
32	
33	### Changes
34	
35	- `processors/norepeat_guard.py` — new `NoProgressRepeatGuard`
36	  (`MultiHookProcessor`). Captures the Bash command in `on_before_tool`
37	  keyed by `tool_call_id`; in `on_after_tool` builds a (command, truncated
38	  output) signature and counts consecutive identical repeats; appends a
39	  corrective "stop repeating / inspect real state" nudge to the tool result
40	  at `repeat_threshold=3`, escalating at `escalate_threshold=6`. Only mutates
41	  `event.result` (contract-safe, mirrors in-tree `CustomEditToolProcessor`).
42	- `config.yaml` — register `NoProgressRepeatGuard` after
43	  `CustomEditToolProcessor` in the processor pipeline via absolute `file://`
44	  path (`repeat_threshold: 3`, `escalate_threshold: 6`, `tool_name: Bash`).
45	
46	### Evidence
47	
48	- `task_000470_f819ab03`: `exit_reason=budget_exceeded`, 80/80 steps; body
49	  shows `CMD "cat << 'EOF' | nc -w 2 127.0.0.1 8080..."` → `OUT '(exit 0, no
50	  output captured)'` repeated ~11x back-to-back; 31/33 total commands
51	  identical.
52	- `task_002108_a8cfbf2a`: `exit_reason=error`, 68 steps; last 8 assistant
53	  tool calls byte-identical `cat > /app/frame_server/src/main.rs << 'ENDOFFILE'`.
54	- `task_000840_b2ac4603` / `task_000908_170e5e4e`: `budget_exceeded` 80/80;
55	  max consecutive identical (command+output) pairs measured 10 and 8.
56	
57	### Uncertainty
58	
59	The nudge redirects the agent to observe state rather than solving the task
60	for it, so a flip depends on the agent then choosing a productive next action
61	— capability, not harness, from that point. If the underlying tasks also have
62	a capability gap (e.g. the Go/Rust server logic was simply wrong), breaking
63	the loop frees budget but may not flip the task. Signal to watch: does the
64	`budget_exceeded` count drop in R2 even if pass_rate moves less? If loops
65	persist despite the guard, the threshold or signature (command-only vs
66	command+output) needs tuning next round.

85	### Why
86	
87	R2 (=R0 config re-measured) scored 25/50. Sweeping failing tasks' `result.json`
88	`final_pytest.output_tail` surfaced a clean, purely-mechanical cluster: three
89	tasks (task_002108 file_operations, task_001857 debugging, task_000796 security)
90	fail with an identical pytest COLLECTION abort — `ImportError while importing
91	test module '/tmp/test_final_state.py'` then `ModuleNotFoundError: No module
92	named 'requests'` then `Interrupted: 1 error during collection`. The hidden
93	verifier probes a running HTTP server with `requests`, which is absent from
94	these base images. The task descriptions never mention `requests` (it is a
95	property of the post-exit verifier), so the agent has no way to infer the
96	dependency. Meanwhile the agents' actual solutions are correct.
97	
98	### Changes
99	
100	- `processors/verifier_dep_guard.py` — new `VerifierDepGuardProcessor`
101	  (MultiHookProcessor). On exit-intent (`on_after_model`, finish_reason in
102	  end_turn/stop and no tool_calls) it injects one real guarded `Bash` tool
103	  call that, for each of a tiny generic allow-list (`requests`, `pyyaml`),
104	  imports-checks then `pip install`s only if missing; every branch ends
105	  `|| true`. Fires once per task; `_order=95` so it defers to the order-90
106	  self-verify processor.
107	- `config.yaml` — register `VerifierDepGuardProcessor` after
108	  `CustomSelfVerifyProcessor` via absolute `file://` path.
109	
110	### Evidence
111	
112	- `task_002108_a8cfbf2a`: verifier tail = `ModuleNotFoundError: No module named
113	  'requests' ... Interrupted: 1 error during collection`. Agent messages show
114	  its Rust frame server tested via stdlib urllib: `Status: 200`,
115	  `Content-Type: image/jpeg`, wrong token gives `401 Unauthorized`, final `ps`
116	  shows `./target/release/frame_server` PID 1293 live (not defunct). Solution
117	  correct; only `import requests` failed.
118	- `task_001857_24daeef3`: same verifier tail. Agent fixed the C++ off-by-one,
119	  ran `./diagnostic_server` (live in ps), own checks returned `{"status":
120	  "healthy"}` on HTTP port and `FRAMES: 450` on TCP port. Solution correct;
121	  only `import requests` failed.
122	- `task_000796_828a72cf`: same verifier tail (partial — server still crashing
123	  at budget, so guard removes the collection mask but may not flip alone).
124	- pip works in-env: `task_001968_3adc0f9b` tool output `Successfully installed
125	  ... certifi-2026.7.22 charset_normalizer-3.5.1 idna-3.19 ...` (requests' own
126	  dependency chain downloaded fine).
127	
128	### Uncertainty
129	
130	Distinct from R1's reverted no-progress loop guard (different lever mechanism,
131	different cluster). Risk: if some target image genuinely cannot install
132	requests (no pip index reachable for that image), the branch reports
133	`unavailable` and the task stays failed — no harm, no flip. Signal to watch in
134	R4: do 002108 and 001857 flip F->T and does the `requests` ImportError
135	disappear from the failing-task tails?
