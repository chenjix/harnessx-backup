20	### Why
21	
22	R0 scored 10/50 (0.20). The single dominant failure cluster is
23	`exit_reason=budget_exceeded` at the step cap (`steps=80`): 11 tasks, only 1
24	passed. On 9 of those 11, the model enters a degenerate tool-level repetition
25	loop — it re-issues the byte-for-byte same `Bash` command 10-33 times in a row,
26	gets the identical result each time, explicitly narrates "I'm stuck in a loop /
27	I need to stop repeating this command," and then repeats it again until the
28	budget is exhausted. The loops set in early (3rd-7th Bash call), so 25-75 steps
29	are wasted on a command already proven useless. This is a harness deficiency:
30	the model cannot self-correct a loop it recognises, and there is no mechanical
31	guard in the pipeline for repeated-identical-tool-call loops (the existing
32	`LengthTruncationRecoveryProcessor` only handles `finish_reason=length` / no
33	tool call, a different shape).
34	
35	### Changes
36	
37	- `processors/bash_loop_breaker.py` — new `BashLoopBreakerProcessor`
38	  (`MultiHookProcessor`): Bash-only fingerprinting; warns on the 3rd identical
39	  command (appends nudge to the tool result), intercepts the 6th (does not
40	  execute; injects a corrective redirect via `approved=False` +
41	  `synthetic_result`). Internal tools (e.g. `_tb2_self_verify`) are never
42	  fingerprinted, so they cannot trip the detector.
43	- `config.yaml` — register the processor after
44	  `LengthTruncationRecoveryProcessor` with `warn_threshold=3`,
45	  `break_threshold=6`. Rest of the pipeline copied byte-for-byte from R0.
46	- `system_prompt.txt` — copied byte-for-byte beside the new config (required by
47	  `SiblingSystemPromptBuilder`).

65	### Uncertainty
66	
67	Breaking the loop returns budget but does not guarantee each task flips — some
68	(e.g. the video-frame + crypto + Go-server task) also need domain capability the
69	model may still lack; those are model-capability gaps, not harness gaps, and
70	this round does not try to patch them. The clean win is removing the specific
71	harness-level waste (burning the whole budget on a proven-useless command). If
72	R2 shows no pass-rate movement AND no cost reduction on the cluster, the loop
73	was masking a deeper capability wall and the lever should move elsewhere.
