20	### Why
21	
22	R0 = 15/50 (30%). Failure taxonomy: **29/35 failures exit
23	`no_tool_calls`=`done`** (agent voluntarily stops) and only 6 hit
24	`budget_exceeded`. The `CustomSelfVerifyProcessor` already fires on
25	28/29 of the `done`-fails AND on every passing run, so the one-shot
26	verify nudge is already present — most `done`-fails are semantically
27	wrong output that passes an existence check, i.e. **model capability
28	gaps, not harness deficiencies** (no harness fix — skip). The one
29	genuinely harness-addressable, cross-task cluster is **exact-command
30	thrash**: runs that re-issue the *literally identical* Bash command
31	many times without any state change, burning the whole 80-step budget.
32	The existing `CustomEditToolProcessor` only counts file-WRITE commands
33	(redirect/sed -i/tee) and is blind to read/poll/debug loops.
34	
35	### Changes
36	
37	- `processors/repeated_command_guard.py` — new `RepeatedCommandGuard`
38	  `MultiHookProcessor`: counts exact-identical Bash command executions
39	  per task; at threshold (5) appends a one-shot "you are looping, take
40	  a fundamentally different action" nudge to that tool's result, then
41	  resets the counter. Append-only, contract-clean, never blocks.
42	- `config.yaml` — register the processor after `CustomEditToolProcessor`
43	  (`_order=31`), `threshold: 5`.
44	
45	### Evidence
46	
47	- `task_000408_0c17d946`: `exit_reason=budget_exceeded`; command
48	  `debugfs /home/user/drive.img 2>&1 << 'EOF'\nls -l /\nEOF` executed
49	  **17 times** (exact Counter over full command strings). Died at
50	  step 80 with no fix.
51	- `task_001716_c1f2ac56`: `budget_exceeded`; the same
52	  `python3 -c "...struct...PIL.Image..."` inline script re-run **22
53	  times** (steps 0–21) before dying at step 80 with no `repo.pack`.
54	- `task_000010_644ab1c2`: done-fail, 76 steps; `sleep 10\nps aux |
55	  grep -E "mock_api|socat|python"` x10 — polling a process that never
56	  started; deliverable `/home/user/operator.py` missing.
57	- `task_000015_89886d8d`: done-fail, 54 steps; `cd /home/user &&
58	  python3 -m pytest test_parser.py` x10 — re-running the same failing
59	  test without changing the fix.
60	- Caveat (regression scope): passing runs also show high repeats —
61	  `task_000123` `echo "Task completed successfully!"` x16 (passed),
62	  `task_001035` x5, `task_000358` x4 — hence exact-match + high
63	  threshold + nudge-only design so these are not harmed.
64	
65	### Uncertainty
66	
67	The exact-repeat signal is present in both failing and passing runs,
68	so the guard is deliberately scoped to nudge (not block) and to fire
69	only at a high count. Risk: the nudge lands but the model still can't
70	find the different approach (the underlying task may be a capability
71	gap) — in that case the round is flat, not negative. If pass-rate
72	drops or a cited passing task regresses, revert (see rollback_trigger).

91	### Why
92	
93	A distinct cluster of HTTP/service tasks scored 0 in R2 not from bad
94	solutions but because the external verifier's pytest module does
95	`import requests`, and `requests` is absent from the task container →
96	pytest rc=2 `ModuleNotFoundError: No module named 'requests'` at
97	collection time → automatic reward 0. The agents built the server in
98	C/Go/Node or Python stdlib and probed with `curl`, so they never had a
99	reason to install the Python client. This is a verifier-side environment
100	gap the harness can close, not a model reasoning error.
101	
102	### Changes
103	
104	- `processors/verifier_dep_primer.py` — new `VerifierDepPrimerProcessor`
105	  (MultiHookProcessor). On the first model turn per task, appends one real
106	  idempotent Bash `ToolCall` (`python3 -m pip install --quiet ... requests
107	  || true`) to `event.tool_calls`; resets on task_start/task_end. Fires
108	  exactly once/task, never replaces the model's own first action.
109	- `config.yaml` — copied R0, registered the new processor under `processors`
110	  with an absolute `file://` target; system_prompt.txt copied byte-for-byte
111	  for SiblingSystemPromptBuilder resolution.
112	
113	### Evidence
114	
115	- rc=2 `ModuleNotFoundError: No module named 'requests'` in R2 trajectories
116	  for tasks 000020, 000028, 000661, 000689, 000958, 002160 (000010 is a
117	  circular-import variant of the same shape). All HTTP/service tasks.
118	- pip is reachable in these containers: passing tasks show flask, certifi,
119	  charset_normalizer installing successfully → `pip install requests` will
120	  succeed and persist into the verifier phase.
121	- Runloop-verified injection path: `on_after_model` output replaces
122	  `model_event` (runloop L438), recorded as assistant message with its
123	  tool_calls (L479), and each tool_call executed with id-matched results
124	  (L497+) → provider-safe N calls / N results.
125	
126	### Uncertainty
127	
128	Two open risks. (1) `requests` may not be the only missing verifier dep —
129	if a task's test imports another lib, that task stays at 0; the fix is
130	scoped to the observed cluster. (2) The turn-0 injection touches all 50
131	tasks; the 12 passers should see only a fast idempotent no-op, but if any
132	turn-0 flow is disrupted or pass-rate drops vs R0, revert.

151	### Why
152	
153	A recurring structural failure shape appears in R3 trajectories that is not a
154	model reasoning error: the external verifier runs in a separate phase after the
155	agent exits and several tests shell out to a standard networking CLI tool via
156	`subprocess.run(["curl", ...])` / `subprocess.run(["ss", ...])`. Those binaries
157	are absent from the base image, so the test raises `FileNotFoundError` at call
158	time and the task scores 0 regardless of the correctness of the agent's work.
159	The agent cannot pre-empt this: during its own phase it hits
160	`curl: command not found`, works around it with wget/python, and correctly
161	concludes it does not need curl for its phase — only the hidden verifier does.
162	This is exactly the structural class of the R3 `requests` pip primer (accepted,
163	flipped 3 tasks), one layer down: OS CLI layer instead of the Python-import
164	layer.
165	
166	### Changes
167	
168	- `processors/verifier_cli_primer.py` — new `VerifierCliPrimerProcessor`
169	  (MultiHookProcessor). On the first model turn per task, appends ONE Bash
170	  `ToolCall` that (guarded by `command -v curl && command -v ss`) does a
171	  quiet, `timeout 90`-bounded, `|| true` best-effort
172	  `apt-get update && apt-get install -y --no-install-recommends curl iproute2`.
173	  Fires once per task; resets on task_start/task_end; never replaces the
174	  model's own first action.
175	- `config.yaml` — copied R3 byte-for-byte, registered the new processor at
176	  `_order=33` (just after the R3 pip primer at 32), `apt_packages: curl iproute2`.
177	  `system_prompt.txt` copied byte-for-byte for SiblingSystemPromptBuilder.
178	
179	### Evidence
180	
181	- `task_001046_eccbf294` result.json `final_pytest.output_tail`: full CPython
182	  `subprocess.py:1863` traceback ending
183	  `FileNotFoundError: [Errno 2] No such file or directory: 'curl'` on
184	  `test_end_to_end_pipeline`; `1 failed, 4 passed` (curl is the ONLY blocker).
185	- `task_001046_eccbf294` messages.json: agent's Bash returned
186	  `bash: line 1: curl: command not found (exit 127)`; assistant reasoned
187	  "curl is not available. Let me try with wget or python." → binary genuinely
188	  absent in-container; agent worked around it but the verifier cannot.
189	- `task_000300_7d6b511c` result.json `final_pytest.output_tail`: identical
190	  `subprocess.py:1863` traceback ending
191	  `FileNotFoundError: [Errno 2] No such file or directory: 'ss'` on
192	  `test_haproxy_running_and_listening` (`ss` = iproute2).
193	
194	### Uncertainty
195	
196	Two open risks. (1) apt may require network access that is blocked in the
197	agent container — if so the install is a bounded no-op and the two tasks stay
198	red (flat round, not negative). The R3 pip primer being accepted implies a
199	usable package channel exists, but apt is a different transport than pip.
200	(2) task_000300 has two further independent failing tests (an AssertionError
201	and a backend-not-running check) that are likely capability gaps, so the `ss`
202	fix is necessary-not-sufficient there; a confident flip is only claimed for
203	task_001046. If pass-rate drops vs R3 or a passing task regresses, revert.
