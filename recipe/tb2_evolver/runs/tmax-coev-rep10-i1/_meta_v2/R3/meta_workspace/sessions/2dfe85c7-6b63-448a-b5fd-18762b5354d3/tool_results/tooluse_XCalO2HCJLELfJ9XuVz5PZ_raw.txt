20	### Why
21	
22	R0 scored 29/50 (58%). Of 21 failures, 6 hit `exit_reason=budget_exceeded`
23	at the full 80-step budget, spanning system_administration, data_querying,
24	scientific_computing, and data_processing. Every one failed the verifier on
25	a "required output file missing" assertion — the agent explored/thrashed the
26	whole budget and left **nothing on disk**. task_000264's own words: "I've
27	been stuck in a loop trying the same query"; then three "Your previous
28	response was cut off... continue" turns with no file write, ending at step 80
29	with `top_managers.csv` / `query_plan.txt` missing. The pipeline ships a
30	`TaskTimeReminderProcessor` but the recipe runner never sets its
31	`timeout_seconds`, so its `on_step_start` returns early every step — the
32	deadline nudge is inert. The budget actually enforced is *steps* (max_steps=80),
33	which nothing tracks.
34	
35	### Changes
36	
37	- `processors/step_budget_deadline.py` — new `StepBudgetDeadlineProcessor`
38	  (`MultiHookProcessor`). On `on_step_start`, computes `step_id / task.max_steps`
39	  and injects escalating user-role reminders at 65% (early) and 85%
40	  (critical) telling the agent to commit its best-effort deliverable to the
41	  required paths NOW and `ls`-verify. Task-agnostic — names no paths/domains.
42	- `config.yaml` — register the processor at `_order=7` (right after the inert
43	  time reminder) via absolute `file://` path, `warn_at: [0.65, 0.85]`.
44	
45	### Evidence

47	- task_000264_ab8c7253: `exit_reason=budget_exceeded`, steps=80, 953s;

52	- task_000010_644ab1c2: `budget_exceeded`, 80 steps; verifier `operator.py

54	- task_000118_3043e92d / task_000958_4bb2b05d / task_001321_658ce4a8: all

56	- Root-cause harness fact: harness.py:246 — `TaskTimeReminderProcessor`

59	### Uncertainty
60	
61	The reminder helps only if a runnable-but-imperfect deliverable exists in the
62	model's head by ~step 52; on tasks where the agent is genuinely lost (no valid
63	approach at all) it won't produce a passing file. Watch attribution: if
64	predicted tasks stay `still_F` while a slow passing task regresses, the nudge
65	is disrupting more than it helps — revert per trigger above.

83	### Why
84	
85	R1 (step-budget deadline nudge) was ACCEPTED: 29/50 -> 30/50 (60%). It got
86	3 of its 6 predicted budget_exceeded tasks (000118, 000958, 001321) to exit
87	`done` instead of running out the step budget — i.e. the agent now commits a
88	deliverable — but those tasks still fail the verifier on *content correctness*.
89	The nudge did its job (commit-on-disk); the wall it hit next is capability.
90	
91	I read all 20 R1 failures via final_pytest assertions + trajectory bodies.
92	The failure landscape splits cleanly and none of it is harness-addressable:
93	
94	- **14 `done`-fail (agent thought it finished, verifier disagreed):** every
95	  one is a genuine correctness/capability gap. Examples — accuracy 0.336 vs
96	  0.98 threshold (000015), F1 0.005 (001321), wrong centroid 36.37 vs 42.01
97	  (001653), grid 60 vs expected 50 (001937), max deviation 1.0 vs <0.1
98	  (000396), lingering processes not killed (000140), process name 'bash' vs
99	  'monitor' (001090), adversarial corpus bypassed (000505). The existing
100	  CustomSelfVerifyProcessor checklist DID fire on these (confirmed
101	  "Verification check initiated" + re-verify turns in bodies) — files exist,
102	  format is right, but the *computed values are wrong*. No processor/prompt
103	  fixes wrong math or wrong logic.
104	- **2 `done`-fail environment issues:** 000028, 000958 — verifier phase errors
105	  with `ModuleNotFoundError: No module named 'requests'` during test
106	  *collection*. initial_pytest PASSED (requests present pre-agent); final fails.
107	  Agent never touched pip/venv (grepped commands). This is a verifier/env
108	  Python mismatch outside config control (internet blocked, can't install).
109	- **6 budget_exceeded (000010, 000264, 001031, 001536, 001701, 001818):**
110	  genuinely hard multi-step tasks — audio transcription+DB load (001818),
111	  parallel matrix decomposition (001031), forensic token classifier (001701),
112	  recursive-CTE hierarchy w/ sqlite locking (000264, agent self-reports "stuck
113	  in a loop"). The step-nudge already fires here; the gap is no valid approach,
114	  not commitment or a recoverable loop.
115	
116	I checked the two candidate harness levers the playbook flags and DROPPED both:
117	- **Plan-block instruction (preservative-transfer):** dropped. Both passing AND
118	  failing multi-part tasks already emit a "Let me break down this task: 1... 2..."
119	  plan in step 1 (compared 000024 pass vs 001937/001090 fail — all plan).
120	  Variant-C second end fails: failing tasks DO plan; gap is execution, not
121	  planning. This is the "encoding a habit that was already free" pitfall.
122	- **Stronger self-verify:** dropped. The existing checklist is comprehensive
123	  (re-read task, ls each output, cat contents for semantic correctness, validate
124	  test method, confirm services alive) and already fires. It can't detect that a
125	  correct-format value is numerically wrong.
126	
127	Shipping a timid threshold tweak or embedding task-specific domain knowledge
128	(the forbidden move) would carry higher regression risk than expected gain.
129	Per SOUL.md, capability gaps get logged, not patched. Explicit no-op is the
130	Pareto-correct decision this round.
