20	### Why
21	
22	R0 = 15/50 (30%). Failure taxonomy: **29/35 failures exit
23	`no_tool_calls`=`done`** (agent voluntarily stops) and only 6 hit
24	`budget_exceeded`. The `CustomSelfVerifyProcessor` already fires on
25	28/29 of the `done`-fails AND on every passing run, so the one-shot
26	verify nudge is already present — most `done`-fails are semantically
27	wrong output that passes an existence check, i.e. **model capability

30	thrash**: runs that re-issue the *literally identical* Bash command

32	The existing `CustomEditToolProcessor` only counts file-WRITE commands
33	(redirect/sed -i/tee) and is blind to read/poll/debug loops.

40	  a fundamentally different action" nudge to that tool's result, then
41	  resets the counter. Append-only, contract-clean, never blocks.
42	- `config.yaml` — register the processor after `CustomEditToolProcessor`
43	  (`_order=31`), `threshold: 5`.

222	### Why
223	
224	A dominant, harness-addressable pathology in the R4 trajectories is the agent
225	re-issuing the *exact same* Bash command and getting back the *exact same*
226	result many times in a row — zero progress until the step budget is exhausted
227	(`budget_exceeded`) or, worst case, the run crashes (`error`) after the same
228	timed-out command is re-run a dozen+ times. This is a control gap: the harness
229	never intercepts the loop. R3/R4 nudge-only guards (EditDetection) were ignored
230	by the model in `task_001017`. The reverted R1 guard (`h_repeated_command_guard_v1`)
231	over-fired because it counted *global* command occurrences and swept up benign
232	echo-spam on passing runs; this round uses a strictly safer signal.
233	
234	### Changes
235	
236	- `processors/noprogress_repeat_breaker.py` — new `NoProgressRepeatBreaker`
237	  (`MultiHookProcessor`): two-stage circuit breaker on consecutive identical
238	  (normalized command, normalized result) Bash pairs. Stage 1 soft nudge at
239	  `soft_threshold=4`; stage 2 hard block (`approved=False` + `synthetic_result`)
240	  at `hard_threshold=6`; separate consecutive-timeout streak blocks repeated
241	  `exit 124` of the same command at the lower `timeout_block_threshold=3`.
242	  `_norm_result` strips sibling-processor advisory suffixes so intermittent
243	  nudges don't break the identical-result match.
244	- `config.yaml` — copied R4 byte-for-byte, registered the new processor at
245	  `_order=32` (just after `CustomEditToolProcessor` at 30), before
246	  `CustomSelfVerifyProcessor`. Kept R3/R4 primers and `apt_packages` intact.
247	  `system_prompt.txt` copied byte-for-byte for SiblingSystemPromptBuilder.
248	
249	### Evidence
250	
251	- Simulation over all R4 trajectories: breaker fires only on reward=0 tasks —
252	  000015, 000118, 000185, 000358, 000408, 000686, 001017, 001035, 001229.
253	  **Zero passing tasks touched.**
254	- No R4 passing task exceeds 3 consecutive identical (cmd,result) pairs
255	  (max passer = task_000020 at 3). Failing budget_exceeded tasks reach
256	  5/6/10/19/24 → thresholds (4/6) sit strictly above the passing ceiling.
257	- `task_001017_9f6adf16`: `exit_reason=error`, ~3830s wall-clock, 15 consecutive
258	  `(exit 124, ...)` timeouts of a brute-force compile/run; timeout-streak block
259	  at 3 caps this at 9 refusals in sim.
260	- Block counts in sim: 000118 (20), 000686 (24), 000358 (18), 000408 (15),
261	  001035 (15) — the death-spiral cluster.
262	
263	### Uncertainty
264	
265	The retroactive sim shows zero passer impact, but blocking changes the live
266	trajectory: a redirected model may or may not find a productive next action
267	within the reclaimed budget (some of these are also genuine capability gaps —
268	scientific_computing, namedtuple circular-import — so a budget flip is not
269	guaranteed). The safe claim is (a) zero regression on passers and (b) a large
270	cost/wall-clock reduction on the thrash cluster; pass-rate upside is plausible
271	but bounded by the underlying capability gaps. If pass-rate drops or a passer
272	regresses with the breaker firing on it, revert.
