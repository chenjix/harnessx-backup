18	### Why
19	
20	r0 = 30/50. Of the 20 failures, 4 are `budget_exceeded` @ 80 steps, 1
21	`loop_detected`, 15 `done`-but-wrong. The single largest *harness-addressable*
22	cluster is a small-`max_tokens` truncation-repetition loop: the model emits a
23	long narration, the provider cuts it off at ~2000 chars (`finish_reason=length`,
24	no tool call), the run loop appends a passive "Your previous response was cut
25	off by the token limit. Please continue from where you left off." user message,
26	and the model regenerates the *identical* paragraph — looping for dozens of
27	steps. Passive-nudge counts: task_000740→11, task_001032→17, task_000396→10,
28	task_000028→5, task_001653→5, task_000015→3, task_000958→3.
29	
30	The existing `LengthTruncationRecoveryProcessor` (v2) was inert on this model:
31	its `content_char_threshold` of 40000 could never match ~2000-char content, and
32	its `on_before_model` *appended* a corrective message — which the before_model
33	contract drops when the last role is already `user` (it is, because the run loop
34	just appended the passive nudge). So the actionable nudge never reached the
35	model; the passive re-priming message stayed the last thing it read.
36	
37	### Changes
38	
39	- `processors/length_recovery.py` — v3: `on_before_model` now *rewrites the
40	  last user message's content* (the passive "continue" nudge) into an actionable
41	  "stop narrating, run ONE command" directive when a truncation streak is armed
42	  (contract-safe len_delta 0); falls back to a +1 append only when the last role
43	  is not `user`. Trigger still keys on `finish_reason==length` (reliable here).
44	- `config.yaml` — repoint the `LengthTruncationRecoveryProcessor` `_target_`
45	  from the R0 v2 asset to the new R1 v3 file; kwargs unchanged.
46	- `system_prompt.txt` — copied byte-for-byte from R0 (sidecar for
47	  SiblingSystemPromptBuilder; identical to DEFAULT so no prompt drift).
48	
49	### Evidence
50	
51	- `task_000740_59416444.messages.json`: assistant turns 11,13,35,39,43,47,51,
52	  58,62,66 are exactly 2001 chars with no tool call; each followed by a
53	  persisted user msg "...cut off by the token limit. Please continue..."; the
54	  next assistant turn re-emits the identical "I've been stuck in a loop..."
55	  paragraph. `exit_reason=budget_exceeded` @ step 80, 1350s.
56	- `task_001032_1adaccb9`: 17 passive nudges, 51 steps, 1018s, still wrong.
57	- `task_000396_e56917e2`: 10 passive nudges, budget_exceeded @ 80 steps, 1248s.
58	- Max assistant content across task_000740 = 2001 chars ≪ v2 threshold 40000
59	  (v2 char branch structurally cannot fire on this model).
60	
61	### Uncertainty
62	
63	The underlying answer may still be wrong on some of these tasks even after the
64	loop is broken (e.g. task_000740's window-function logic bug). But freeing the
65	wasted step budget gives the model turns to self-correct instead of grinding to
66	the cap, and 4 of the cluster are pure step-burns. If R2 shows no movement on
67	the budget_exceeded set, the loop-break is not the binding constraint — revert
68	and look upstream at the model's reasoning-length habit.

87	### Why
88	
89	R1 landed at 28/50. Sweeping all failing result.json, exactly two tasks —
90	task_000958 (data_querying) and task_000028 (system_administration) — fail
91	because the *verifier's* test module cannot `import requests`: the tail is
92	`ModuleNotFoundError: No module named 'requests'` -> `Interrupted: 1 error
93	during collection` (rc=2). The test suite never runs a single assertion, so
94	even a correct service scores zero. Both tasks ask the agent to build a C++
95	HTTP microservice that the external verifier probes with `requests`. Because
96	the agent and verifier share one container filesystem, an agent that tested
97	its own service with a `requests`-based client (installing the package first)
98	would leave `requests` importable and let the verifier collect its tests.
99	
100	### Changes
101	
102	- `system_prompt.txt` (sibling read by SiblingSystemPromptBuilder) — kept the
103	  R1 base byte-for-byte and appended a general strategy paragraph: when a task
104	  runs a network/HTTP service, verify it end-to-end from a real client,
105	  preferring Python `requests` (install it if absent; don't assume
106	  curl/wget/nc), exercising every specified endpoint/auth/error case, and
107	  confirming the process is still alive at finish. No task IDs, ports, or
108	  paths from the training set are embedded — it is a class-level testing habit.
109	- `config.yaml` — copied byte-for-byte from R1 (processor pipeline unchanged);
110	  only the sibling prompt sidecar changed.

153	### Why
154	
155	R2 = 29/50. Of 21 failures, exactly 7 are dominated by a max_tokens truncation
156	spiral: task_000010 (18 passive nudges / 25 collapses), task_001031 (20/36),
157	task_001032 (20/20), task_000028 (13/15), task_001321 (12/14), task_000118
158	(10/11), task_001089 (9/27). These are the round's longest runs (65-92 messages)
159	and include all remaining budget_exceeded cases. The other 14 failures are short
160	runs (under 50 messages, 0 truncation) with genuine partial-test accuracy bugs -
161	model capability gaps, not harness-addressable this round.
162	
163	R1 v3 processor (repointed, still live in R2) does the right thing at the
164	on_before_model layer: it rewrites the run loop passive "continue from where you
165	left off" nudge into an actionable "run ONE command" directive, and the bodies
166	confirm the model reads and acknowledges it. But it keeps spiralling. Two
167	mechanical amplifiers, invisible until this round body read, keep the loop
168	alive:
169	1. Re-seeding tail: v3 collapsed oversized turns to head(1200)+marker+tail(600),
170	   and the preserved tail is exactly the mid-reasoning continuation the next
171	   turn latches onto and keeps developing.
172	2. Barely-triggered collapse: most truncated turns are ~2000 chars, right at
173	   the v3 ~2000 collapse threshold, so v3 often left the whole runaway turn in
174	   history; 10-30 of them accumulate (input_tokens climb 24k-to-40k on
175	   task_000010), costing budget and re-priming the same unfinished thought.
176	
177	The truncation is NOT degenerate token-repetition - it is genuine verbose
178	chain-of-thought ("Wait, I think I see the issue now! Let me trace through the
179	code...") running past the 4096 output-token cap before reaching a tool call.
180	max_tokens is a runtime-only slot (env TMAX_MAX_TOKENS) outside the config
181	surface, and a louder prompt cannot make a 9B model self-limit reasoning it
182	acknowledges but cannot shorten. The only remaining lever is mechanical: stop
183	feeding the model its own unfinished spiral.
184	
185	### Changes
186	
187	- processors/length_recovery.py - v4: on_after_model now collapses every
188	  truncated no-tool-call turn to a short head stub (head_chars=400) with NO
189	  tail (tail_chars=0), replacing the discarded middle+tail with a terminal
190	  marker that tells the model the reasoning is gone and not to reconstruct it.
191	  Collapse threshold drops to head+tail+len(marker) (~600) so it fires on every
192	  ~2000-char truncated turn. on_before_model unchanged from v3 (contract-safe
193	  rewrite of the last user nudge; +1 append when last role is not user); the
194	  escalated repeat nudge now offers a concrete short-output path (single heredoc
195	  write) instead of asking the model to self-limit reasoning.
196	- config.yaml - repoint LengthTruncationRecoveryProcessor _target_ from the R1
197	  v3 asset to the R3 v4 file; add head_chars: 400, tail_chars: 0 kwargs. Rest of
198	  the pipeline unchanged.
199	- system_prompt.txt - copied byte-for-byte from R2 (sibling for
200	  SiblingSystemPromptBuilder; no prompt drift).
201	
202	### Evidence
203	
204	- task_000010_644ab1c2 oh_runs trace: steps 50/53/55-59/61/67-69 all
205	  stop_reason=length, output_tokens=4096, no tool call; input_tokens climb
206	  24625 -> 40018 across accumulating ~2000-char reasoning turns.
207	- task_001032_1adaccb9.messages.json steps 35/37/39/41: assistant quotes the v3
208	  nudge back ("The user is telling me to stop the repetitive analysis and just
209	  run a single Bash command...") then narrates the full 2009-char turn and
210	  truncates again; the collapse tail preserves the exact mid-reasoning
211	  continuation re-seeding the next turn.
212	- Contrast: task_000010 steps 60/62/63 emit tool_use at output 1039-1450 tokens
213	  (under 4096) - a short-context turn fits within budget, so shrinking context
214	  and killing the re-seed is the right lever.
215	
216	### Uncertainty
217	
218	Even with the loop broken, some tasks carry upstream logic bugs (task_001032
219	path-safety, task_000028 frame-count accuracy) that may keep them failing after
220	the step budget is freed. The bet is that freeing budget plus a clean short
221	context lets the model reach and iterate on a tool call instead of grinding to
222	the cap. If R4 shows the cluster still spiralling with no flips, the constraint
223	is the model reasoning-length habit and the lever is exhausted - revert to v3.
