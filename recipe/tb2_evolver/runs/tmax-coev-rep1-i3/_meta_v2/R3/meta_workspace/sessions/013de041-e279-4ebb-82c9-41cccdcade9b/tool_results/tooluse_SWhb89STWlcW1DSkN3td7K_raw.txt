20	### Why
21	
22	R0 scored 27/50 (54%). system_administration was the worst cluster at 0/5.
23	Two of those failures share one mechanism: the agent leaves background
24	service processes lingering / mis-records a PID, and the verifier fails on
25	lifecycle assertions even though the task's logic is correct.
26	task_000140 failed only `test_no_lingering_service_processes` (lingering
27	`vm_service` PIDs); task_001090 failed only `test_pid_file_and_process`
28	(`pid.txt` contained `576\n578\n641`). The R0 config already carried a
29	`ProcessLifecycleSelfVerifyProcessor` whose checklist explicitly warns about
30	lingering processes and wrapper PIDs — and both agents *read it and
31	self-reported compliance* without ever running the check. A text reminder
32	the model narrates past is not a fix; the model needs raw state it did not
33	author.
34	
35	### Changes
36	
37	- `processors/lifecycle_snapshot_verify.py` — new
38	  `LifecycleSnapshotSelfVerifyProcessor` (subclass of the stock
39	  `CustomSelfVerifyProcessor`, same singleton group `tb2_self_verify` so it
40	  replaces the R0 processor). On the first exit-intent turn it injects a
41	  **real `Bash` diagnostic tool call** dumping the live user-process table
42	  and the contents of every `*.pid`/`pid.txt` file, then injects a
43	  reconciliation + stock-checklist user message on the next `on_before_model`.
44	- `config.yaml` — swapped the R0
45	  `process_lifecycle_verify.py::ProcessLifecycleSelfVerifyProcessor` entry for
46	  the new processor (`file://` absolute path).

98	### Why
99	
100	R1 accepted at 29/50. Sweeping R1 failures surfaced a recurring,
101	harness-visible mechanism the R1 config's v4 LengthTruncationRecovery
102	Processor detects but cannot break: on four failing tasks
103	(task_001032 x14, task_000740 x9, task_000010 x4, task_000028 x4) the
104	model emits length-truncated pure-reasoning turns (tool_calls == 0,
105	finish_reason == length) turn after turn, never reaching a tool call.
106	The v4 collapse fires correctly (assistant turns end with its discard
107	marker) and v4's escalated text nudge ("write NO analysis, emit ONE
108	command") is present — and the model narrates right past it, exactly the
109	narrated-past failure the R1 lifecycle work already documented. Tasks
110	with only a single truncation event (000396, 000578, 001673, 001701)
111	all passed, so heavy truncation is a discriminating failure signal, and
112	the spiral consumes the whole step/token budget (001032 ran 1109s and
113	never fixed the tar parser; 000740 exited loop_detected; 000010 exited
114	budget_exceeded).
115	
116	### Changes
117	
118	- processors/length_recovery_forceact.py — new v5
119	  LengthTruncationRecoveryProcessor (same singleton group
120	  tb2_length_recovery, so it replaces the R1 v4 processor). Keeps v4
121	  collapse + escalating text nudge, adds a mechanical force_action_
122	  threshold (default 3): once that many consecutive truncations
123	  accumulate, on_after_model injects a real generic Bash workspace-
124	  snapshot tool call (pwd/ls -lat/find -mmin -30/ps, all guarded) so
125	  fresh tool output lands in context and breaks the reasoning-only
126	  momentum — the same injected-real-tool-call mechanism the R1 lifecycle
127	  processor proved fires in this harness. The injected call clears the
128	  streak, so it fires at most once per spiral. Also rewrote the repeat
129	  text nudge to steer toward small-payload edits (sed -i, chunked >>

131	  cannot fit under the output cap and re-truncates.

134	  force_action_threshold=3, head_chars=400, tail_chars=0,
