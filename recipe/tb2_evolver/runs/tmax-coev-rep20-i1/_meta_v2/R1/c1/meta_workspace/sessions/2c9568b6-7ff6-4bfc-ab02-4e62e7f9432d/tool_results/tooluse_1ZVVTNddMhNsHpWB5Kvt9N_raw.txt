### Why

The single most common failure of R0 is the agent getting stuck emitting
the **exact same Bash tool call verbatim** until the 80-step budget is
exhausted. Assigned task `task_000010_644ab1c2` is the archetype: it wrote
`/home/user/operator.py`, which shadows the stdlib `operator` module and
poisons every `python3` invocation from the CWD, then re-ran the identical
`python3 -c "import socket"` probe 33 times — identical narration, identical
error — with zero variation, never diagnosing the shadowing. The pipeline
had no guard for this: the only loop processor present
(`LengthTruncationRecoveryProcessor`) fires solely on `finish_reason=length`
with no tool call, a different mode. These calls are well-formed and succeed.

### Changes

- `config.yaml` — added built-in
  `harnessx.processors.control.loop_detection.LoopDetectionProcessor`
  (defaults: window 12, warn 3, raise 5, name_warn 8, compaction_drop 5),
  placed last in the pipeline. No new code authored.

### Evidence

- `task_000010_644ab1c2` result.json: `exit_reason=budget_exceeded`,
  `steps=80`; messages.json shows 33 assistant turns, all with the identical
  tool_call `python3 -c "import socket..."` (distinct fingerprints = 1).
- Cluster scan of all 38 `budget_exceeded` trajectories:
  `max_identical_consec >= 5` on ~24 tasks; 17 tasks have `distinct==1`
  (same call 33x). LoopDetectionProcessor Strategy 1 fires on all of these.
- `task_000344_e265c898` (currently PASSING, distinct=1): the repeated call
  is a read-only `python3 -c` reasoning spin *after* the reward-earning work
  already landed; early termination keeps the pass and saves ~28 steps.
