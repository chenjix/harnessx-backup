20	### Why
21	
22	Baseline: 30/50 pass (0.6). Among the 20 failures, one cluster is
23	cleanly harness-addressable: three reward=0 tasks fall into runaway
24	exact-repeat loops, emitting the *identical* tool call dozens of times
25	until they exhaust step/time budget with no progress. This is a harness
26	deficiency (no interrupt on a non-recoverable repeat state), not a model
27	capability gap. The other failure buckets — 8 `chat ... timed out`
28	agent_errors (model-server slowness, outside the HarnessConfig surface),
29	and diverse sysadmin/reward=0 capability gaps — are not clusterable into
30	one harness fix and are logged below as skips.
31	
32	### Changes
33	
34	- `config.yaml` — register `harnessx.processors.control.loop_detection.LoopDetectionProcessor`
35	  on `_hook_: '*'` with `window_size=12, warn_threshold=3, threshold=6,
36	  name_warn_threshold=999, compaction_drop_threshold=5`. Strategy 1
37	  (exact name+input) warns at 3 consecutive repeats and raises
38	  `LoopDetectedError` at 6; Strategy 2 (name-only) warnings disabled.
39	  `LoopDetectedError` maps to `exit_reason=loop_detected` (not `error`),
40	  so it does not trip the post-flight replay gate.
41	
42	### Evidence
43	
44	- `task_000010`: 48 exact-consecutive identical tool calls, reward=0.
45	- `task_001031`: 41 rewrites of analyze.py (35 exact-consecutive),
46	  66 steps / 548s, reward=0.
47	- `task_000958`: 31 exact-consecutive identical calls, reward=0.
48	- Contrast: max exact-consecutive-repeat among all 30 *passing* tasks
49	  is 2 → threshold=6 leaves a 3x safety margin.
50	- `task_001818` (separate thrash, timed out): rewrote main.rs 12x,
51	  rebuilt 11x over 54 calls — different-args thrash, not exact-repeat;
52	  Strategy 1 will not catch it (correctly, since it is not the target
53	  cluster) and Strategy-2 is disabled to avoid false positives.
54	
55	### Skips (model-capability / out-of-surface — no harness fix)
56	
57	- 8 tasks `chat failed at step N: timed out`: single model API
58	  generation call times out (fires even at step 7 / ~8.7K chars, far
59	  below compaction threshold). Root cause is model-server slowness;
60	  retry/timeout lives in the provider/model-client layer, not the
61	  evolvable HarnessConfig surface. No harness fix — skip.
62	- Sysadmin cluster (0/5) and remaining reward=0 `ok` exits: diverse
63	  genuine capability gaps (missing flock, unresolved deadlock, wrong
64	  process persistence/naming, incomplete at max_steps). Not one class
65	  — no single harness fix — skip.
66	
67	### Uncertainty
68	
69	The bet is that aborting the loop early frees enough budget for the
70	model to recover on those 3 tasks; it is possible the underlying
71	capability gap means they still fail (just cheaper/faster). Even then,
72	the change is net-positive on cost and carries near-zero regression
73	risk (3x threshold margin, Strategy-2 disabled). If any passing task
74	regresses to `loop_detected`, revert.

93	### Why
94	
95	Mechanism correction first: the tmax eval loop (`recipe/tmax_eval/run_eval.py`
96	+ `agent_loop.py`) does **not** run the `config.yaml` processor pipeline. It
97	resolves only the system prompt via `_resolve_system_prompt`
98	(`system_prompt.txt` sibling of the config, else first `templates/*.j2`, else
99	the built-in default). R1's loop-detection *processor* was therefore inert,
100	and R1's `system_prompt.txt` was byte-identical to the built-in default — so
101	R0≈R1 and the reported +3/-4 (30→29) flip is run-to-run noise from the
102	stochastic 9B server, not a real regression. The only live lever on this
103	benchmark is the system prompt.
104	
105	The dominant harness-addressable failure cluster is premature stopping: 9/21
106	R1 failures finish `no_tool_calls`, and their verifier failures are on
107	*explicit, checkable* requirements the agent never re-verified — exact string
108	`E0502` (agent wrote `0502`), process name `monitor` (ended up `bash`), a
109	build artifact at the wrong path, a required file never created. The built-in
110	prompt actively invites early exit ("When the task is complete, stop calling
111	tools"). This is an instruction deficiency, not a capability gap — Bash can
112	check all of these.
113	
114	### Changes
115	
116	- `system_prompt.txt` — new strategy-level prompt: SURVEY & PLAN (enumerate
117	  every explicit requirement — exact paths/filenames/strings/process names)
118	  → IMPLEMENT (write to exact paths, preserve literal strings) → VERIFY
119	  BEFORE STOPPING (re-check each requirement against real filesystem/process
120	  state via Bash; fix and re-verify before stopping). No task literals.
121	- `config.yaml` — byte-identical copy of R1 (processor pipeline is inert on
122	  this loop; left unchanged to avoid churn).
123	
124	### Evidence
125	
126	- `task_000748_c9807703` (no_tool_calls, 18 steps): final assistant message
127	  narrates "extract just the numeric code (e.g., '0502' from 'E0502')";
128	  verifier `assert 'E0502' in '0502\n'` fails. Agent dropped a required char
129	  and never re-read the requirement.
130	- `task_001090_c61c71f2` (no_tool_calls, 32 steps): final message "The task
131	  is complete. Let me summarize..."; verifier finds process `comm=='bash'`,
132	  expected `'monitor'`.
133	- `task_000933_1f27096a` (no_tool_calls, 8 steps): final message "All
134	  requirements have been completed successfully"; verifier: binary path
135	  `bin/graph_math_double` missing.
136	- `task_000015_89886d8d` (no_tool_calls, 78 steps): required file
137	  `/home/user/test_parser.py` never created.
138	- Headroom check: 29/29 passing tasks stop at `no_tool_calls`, median 13 /
139	  max 64 steps vs cap 80.
140	
141	### Skips (model-capability / out-of-surface — no harness fix)
142	
143	- 8 tasks `chat failed at step N: timed out` + 1 `HTTP 400` finish `error`:
144	  `agent_loop._chat` has no retry, so a single transient model-server timeout
145	  aborts the session and discards progress. This is a genuine harness
146	  deficiency, BUT `agent_loop.py` is under `recipe/` (read-only) and is not
147	  reachable from the evolvable `config.yaml`/system-prompt surface. Logged for
148	  a human: a retry-with-backoff wrapper around `_chat` would likely recover
149	  several of these. No harness fix available from this surface — skip.
150	  (See `_meta_scratch/candidates.md` mechanism note.)
151	
152	### Uncertainty
153	
154	The bet is that explicit verify-before-exit discipline flips premature-stop
155	failures without pushing passing tasks toward the step cap. If some failures
156	are true capability gaps (the agent can't produce the right value even when it
157	knows to check), they stay failed — but the change stays net-positive on
158	correctness and near-zero on regression risk given the large step headroom.
159	If R3 pass_rate is flat/down while step counts climb, revert to the default
160	prompt.

179	### Why
180	
181	Re-verified mechanism: the tmax eval loop (recipe/tmax_eval/run_eval.py::_resolve_system_prompt + agent_loop.py) does NOT run the config.yaml processor pipeline — it resolves only the system prompt (sibling system_prompt.txt) and runs a fixed single-Bash-tool loop (temperature=0, max_steps=80). System prompt is the sole live lever.
182	
183	R2 (28/50, ~flat vs 30/50 baseline within 9B run-to-run noise) added a generic verify-before-exit phase. Inspecting R2's residual failures shows the phase is followed superficially: the agent produces confident ✅ "all requirements verified" checklists after a happy-path run, but the verifier fails on the EXACT grading semantics the agent never adversarially tested — a process's comm-name (checked `/proc/PID/comm`), a forbidden substring left in a comment, an exact line count / format. This is an instruction-shape deficiency (how to verify), not a capability gap: every one of these checks is a one-line Bash command the agent could have run.
184	
185	### Changes
186	
187	- `system_prompt.txt` — evolve phase 3 from generic "re-check each requirement" into an ADVERSARIAL, grader-mirroring verify: for each stated constraint run the exact strict test a grader would (existence/exact-path; grep artifact for required literals; grep artifact — comments included — for forbidden "must not" tokens; check process identity via /proc/<pid>/comm and pgrep -a/-f, not just PID-alive; assert exact counts/formats/ordering via wc -l etc.; actually run produced scripts). Treat a happy-path run or a self-test that itself errored as NOT proof. Stop once every strict check passes. No task literals — only generic Linux idioms.
188	- `config.yaml` — byte-identical copy of R2 (processor pipeline inert on this loop).

223	
224	### Why
225	
226	Re-verified mechanism (again, by reading `recipe/tmax_eval/agent_loop.py::run_agent` + `run_eval.py::_resolve_system_prompt`): the tmax eval loop ignores the config.yaml processor pipeline entirely and consumes only the resolved system prompt string (sibling `system_prompt.txt`). Fixed single Bash tool, temperature=0, max_steps=80. The system prompt is the ONLY live lever. So the R1 `LoopDetectionProcessor` is inert.
227	
228	R2/R3 pushed the verify-before-exit instruction line twice; scores stayed in the 28-30/50 run-to-run-noise band. That lever is exhausted, and most residual `no_tool_calls` failures are genuine value-computation gaps (F1, grid=50, deadlock). But a DISTINCT, larger, clearly harness-addressable cluster was hiding in the exit_reason data: runaway identical-command repeat loops. Measured max-consecutive-identical Bash commands per task: the 7 loop tasks (task_000010=39, task_000028=43, task_000118=54, task_001701=45, task_000015=59, task_001652=6, task_000505=8) are ALL fails; every passing task is <=3 except one benign `echo` loop. This is a control-flow deficiency: at temperature 0, re-issuing the same command yields the same result, so the model deterministically wastes its whole budget re-running a stuck command instead of diagnosing the root cause.
229	
230	### Changes
231	
232	- `system_prompt.txt` — kept the accepted R3 adversarial verify-before-exit prompt verbatim and ADDED a general "NO-PROGRESS DISCIPLINE" section between IMPLEMENT and VERIFY: if the same/trivially-varied command produces the same result 2-3 times, treat it as a hard no-progress signal, stop repeating, diagnose the root cause (read errors/logs; question assumptions — a created file may shadow a system module, a background service may be dying, a poll may never converge), then change approach or stop cleanly. Short polling is explicitly allowed. Also added two small VERIFY hardening bullets (general): (a) data-type/format read-back (a JSON number must be a real number not a quoted string — targets task_000578's `"24.0000"` string bug and the process-respawn check for task_000140), and (b) "an unrun check is a failed check" to curb hallucinated ✅ checklists. No task literals (grep-verified clean).
233	- `config.yaml` — byte-identical copy of R3 (pipeline inert on this loop).
234

Verifier's own runpy also breaks (`operator.py` in cwd).

239	- task_001701: identical `jshon ... -e 0 -k cert_b64` 45x.

241	- Contrast: 30 passing tasks all <=3 max-consecutive-identical except task_000684 (PASS, 42x harmless `echo "Task completed successfully!"` after the artifact was already correct — safe to abort early).

248	### Uncertainty
249	
250	The bet: breaking deterministic repeat loops reclaims budget for real diagnosis (and avoids the task_000015 context-blowup 400). If the underlying task is a true capability gap the agent still fails — but cheaper, and without crashing the session. Near-zero regression risk given the <=3 passing-task repeat ceiling and the benign echo exception. If R5 drops below the band or a passing task regresses to an early stop, revert to the R3 prompt.
