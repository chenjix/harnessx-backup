89	### Why
90	
91	Assigned focus task_000118_3043e92d (system_administration): the true reward
92	failure is a logic/timing bug — the agent's `deployment_monitor.py` never
93	truncated logs during the grader's run, so peak log-dir size hit 209,715,200
94	bytes vs the 45,000,000 threshold. But the harness actively made this harder:
95	the stock `CustomEditToolProcessor` scans the ENTIRE Bash command for `>`

98	`SIZE_THRESHOLD = ...` and `if size > max_size:`. The `>` inside the body was

101	accumulated in the per-file edit counter and fired THREE simultaneous
102	`[EditDetection]` over-edit warnings. The model's own summary shows it read
103	these as "The system is detecting excessive edits" and reacted by deleting and
104	recreating the file — an unproductive loop that consumed steps it needed for
105	the real timing bug. This is a genuine harness deficiency (a mechanical parser
106	false-positive injected into tool results), not a model knowledge gap, so it is
107	fixable in the harness regardless of whether it alone flips the task.
108	
109	### Changes
110	
111	- `processors/heredoc_aware_edit_detector.py` — new
112	  `HeredocAwareEditToolProcessor` (MultiHookProcessor). Drop-in replacement for
113	  the stock `CustomEditToolProcessor`: same singleton group
114	  (`bash_edit_detector`), same `_order` 30, same `threshold` knob, same hook
115	  surface and warning text. Only difference: `_strip_heredoc_bodies` removes
116	  every heredoc body (keeping the opener line so the redirect target is still
117	  counted) before running the stock redirect/sed/tee regexes, so body `>`
118	  characters are treated as data.
119	- `config.yaml` — replace `benchmarks.terminal_bench_2.harness.CustomEditToolProcessor`
120	  with the new processor via absolute `file://` path, `threshold: 7`.
