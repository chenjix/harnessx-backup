91	### Why
92	
93	Assigned focus `task_000028_7fe033ac` (system_administration) has
94	`status="error"`, `reward=0`, `elapsed_s=0.1`. It is NOT a harness or model
95	capability failure — the agent never ran. The container failed to start:
96	`docker: Error response from daemon: Conflict. The container name
97	"/tmax-task0000287fe033ac-1788258698" is already in use ...`, raised at
98	`recipe/tmax_eval/docker_env.py:124` (`start_container`).
99	
100	Root cause is in read-only runner code, `docker_env.py:105`:
101	`name = f"tmax-{task_id.replace('_','')[:20]}-{int(time.time())}"[:63]`.
102	The second-resolution `int(time.time())` collides on retry / same-second
103	concurrency, so `docker run --name` hits an existing container and the
104	RuntimeError fires before the run loop boots. All 8 `status="error"` tasks in
105	this trajectory set share this identical signature (each elapsed_s ≈ 0.1):
106	task_000015, task_000028, task_000140, task_000505, task_000748, task_001032,
107	task_001090, task_001781.
108	
109	Per tb2-playbook + hard invariant #2, container lifecycle/naming is outside the
110	config.yaml evolvable surface (processors / tool_registry / system prompt only)
111	and lives in read-only recipe code. The failure precedes the first agent turn,
112	so no MultiHookProcessor hook can ever fire on it. There is no in-scope harness
113	fix. Shipping explicit no-op (byte-for-byte R1 copy) rather than drifting onto
114	another proposal's territory.
