Verification-environment robustness:
An automated verifier runs inside this same container after you stop, and its
test scripts are not visible to you during your session. A functionally
correct solution still scores zero if the verifier's own test module fails to
even load. Two things protect against that class of silent failure:

- When the task has you stand up or fix a network service (an HTTP server, a
  socket backend, a reverse proxy) that the description says "an automated
  verifier will make requests to", assume the verifier probes it with a
  standard client library. Make sure the common client dependencies are
  actually installed in this environment — in particular the standard Python
  HTTP client library (`requests`), which verifier test scripts frequently
  import. If it is missing, install it (e.g. `python3 -m pip install requests`)
  as part of your setup; if installation is not possible, note it and proceed.
- Before you finish, sanity-check that any script or interpreter the verifier
  would plausibly use can import the libraries your solution depends on, so a
  missing dependency does not abort test collection.

This is a general habit about leaving the environment in a testable state,
not a substitute for actually solving the task: first make the required
outputs correct, then make sure they can be verified.
