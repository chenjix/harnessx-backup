22	### Why
23	
24	Baseline 20/50 (0.40). Beyond the large `budget_exceeded` thrash cluster
25	(~12 tasks stuck in repetition loops on genuinely hard crypto / reverse-
26	engineering / multi-service tasks — model capability gaps, not harness),
27	there is a clean **harness-shaped** cluster: 4 tasks whose verifier aborts
28	at **pytest collection time** with `ModuleNotFoundError` — the grader does
29	`import requests` / `import imageio` against a container whose base image
30	lacks the package. Solution quality is irrelevant; the test file cannot
31	even be collected, so `reward=0`.
32	
33	The R0 config already carried a `VerifierDepGuardProcessor`, but it fired
34	**only on the agent's clean exit-intent turn** and its allow-list was just
35	`(requests, pyyaml)`. Trajectory grep of `VERIFIER DEP CHECK` shows it
36	fired on the 36 clean-exit tasks but on **none** of the 3 ImportError
37	tasks that ended via `budget_exceeded` / `error` — the exact tasks that
38	needed it. And task_000773 (a clean finish) still failed because `imageio`
39	was not in the allow-list.

41	### Changes
42	
43	- `processors/verifier_dep_guard.py` — rewrote `VerifierDepGuardProcessor`
44	  to fire **once early** (first `on_after_model`), appending a forced Bash
45	  ensure-deps call alongside the agent's own first tool calls, instead of
46	  gating on a graceful exit. Expanded allow-list to the ubiquitous verifier
47	  libs: `requests, imageio, Pillow(PIL), numpy, scipy, pyyaml`. Still a

49	- `config.yaml` — repointed the guard `_target_` `file://` to the R1 copy;

104	### Why
105	
106	R0=20/50, R1=20/50 (flat; R1's +4/-4 task swap classified as run-to-run
107	noise). The dominant *harness-shaped* signal in R1 is a content-repetition
108	loop: 4 of the 5 `budget_exceeded`/`max_steps` failures (all pinned at the
109	80-step cap) emit degenerate near-identical assistant narration turn after
110	turn. task_000910 shows 15 consecutive identical assistant turns;
111	task_001028 shows 9 consecutive identical turns and 24 turns sharing the
112	same 60-char prefix. Existing guards miss this: LengthTruncationRecovery
113	fires only on `finish_reason=="length" and not tool_calls` (these finish
114	normally / carry tool calls); CustomEditTool counts only repeated file-write
115	commands (these are diagnostic/compile commands); CustomSelfVerify fires once
116	on exit-intent only. No live mechanism detects a normal-finish narration loop
117	mid-run — a detection/interception gap, the canonical MultiHookProcessor case.
118	
119	### Changes
120	
121	- `processors/content_repetition_recovery.py::ContentRepetitionRecoveryProcessor`
122	  — new MultiHookProcessor, `_order=6` (right after length-recovery).
123	  Fingerprints normalized assistant content on `on_after_model`; after
124	  `repeat_threshold=3` consecutive look-alike turns injects a corrective nudge
125	  (change tactic / gather new evidence), escalating at `escalate_threshold=5`
126	  to a hard "STOP — write the required output file to its exact path or run one
127	  genuinely new command". +1 user message per chain max; `min_content_chars=40`
128	  avoids tripping on terse action turns. Counter resets after each nudge.
129	- `config.yaml` — register new processor after LengthTruncationRecovery;
130	  carry R1's VerifierDepGuardProcessor forward byte-for-byte (repointed to
131	  R2-local copy); SiblingSystemPromptBuilder sidecar `system_prompt.txt`
132	  copied into R2/.
133

136	- `task_000910_16cc0daf` (probe5.py over R1 messages.json): 15 consecutive
137	  identical assistant turns ("Let me try a different approach - use a simpler
138	  command to compile and test."); exit=budget_exceeded, 80 steps.
139	- `task_001028_5bc8bc70`: 9 consecutive identical turns ("I've been stuck in a
140	  loop trying to understand the binary. Let me take a completely different

145	- Counterfactual: had this been live in R1, task_000910 interrupts after turn 3

147	  toward writing the required output file before the cap — the specific gap
148	  that scored these 0 (files never created).

150	### Uncertainty
151	
152	Neither loop task is guaranteed to flip (both are genuinely hard: multi-service
153	daemon + binary RE). Worst realistic case is no flips but large step/cost
154	savings on the loop cluster. Main risk is a false-positive nudge on a
155	legitimately iterative task; no passing R1 task showed a 3+ identical-narration
156	streak (passing tasks finished in 6-33 steps), so predicted collateral is near
157	zero. Trigger threshold is unvalidated at runtime — if R3 shows the nudge firing
158	without breaking loops, or any regression with a nudge in-transcript, revert.
